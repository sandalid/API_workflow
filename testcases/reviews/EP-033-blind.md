# EP-033 — Blind Inventory (Phase A)
**Endpoint:** GET /categories | **Module:** Categories | **Sheet title:** "Verify the category tree correctly reflects only categories intended to be customer-facing, per taxonomy rules confirmed with BA."

**Note:** `qa-knowledge\` (business-rules.json, gaps-and-conflicts.md, modules\categories.md) was not available to this reviewer at review time (file/dir not found). This inventory relies only on the audit, spec, and fixtures; KB coverage is flagged as "could not judge" below rather than invented.

## Scope ground truth (from audit, binding for this inventory)
- Public, unauthenticated, no roles/ownership/resource-states. `Category` model has no visibility/status/soft-delete column.
- `GET /categories` is the **flat list** (`findAll`), not the tree (`GET /categories/tree` is the real tree — a different operation).
- No "customer-facing" filter exists anywhere in code or schema.
- Spec: no parameters, no security, 200 response has empty description and **no schema, no content/media-type object at all** (`openapi.pretty.json:1210-1224`).
- fixtures.json contains **zero** entries for `/categories` (no key, no seeded category ids, no role/account fixtures, no empty-DB or legacy-category fixtures). The file's only content is listings-endpoint fixtures and a `_owners`/`_states` map unrelated to this endpoint.

## Conflict rows requiring BLOCKED treatment (from the audit's Source agreement matrix)
1. **"Only customer-facing categories" filter** — sheet claims a BA-confirmed rule; nothing in code/schema implements it. (Inventory #7) → BLOCKED, with an explicit clarifying question, never a confident PASS/FAIL.
2. **Legacy categories excluded from the public list** — implied by the sheet title; code comments describe coexistence with no exclusion logic, but this is code-comment evidence only, not a verified live-DB fact. (Inventory #6) → BLOCKED.
3. **Endpoint path is the "tree"** — sheet's title/path don't describe the same operation as `/categories/tree`. (Inventory #8) → BLOCKED, with a question of whether the sheet row should be re-pointed at `GET /categories/tree`.

## What the spec lets Schemathesis verify
- Parameters: none declared — fuzzing of query/path/header params is moot (spec says `parameters: []`).
- Security: none declared — Schemathesis has no auth-negative scenario to generate from the spec itself (any auth-variant cases must be hand-written, not spec-derived).
- Response: `200` has an empty `description` and **no schema, no `content` object at all**. This means:
  - Schemathesis's response-schema-conformance check is vacuous here — it will pass trivially because there is nothing to check.
  - Content-type conformance cannot be checked either (no media type declared).
  - Only the "status-code is documented" check is meaningful, and it will actively mis-flag every legitimate non-200 (404/405 for unsupported methods, 429 for rate-limiting) as nonconformant, since only 200 is documented — this is expected noise, not a new defect, and should be annotated as such rather than reported as a fresh spec violation.
