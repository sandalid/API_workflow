## Declared Contract

- **Path param:** `id` (listing id). No query params, no request body.
- **Headers:** `Authorization: Bearer <jwt>` required (`JwtAuthGuard`, `@Roles('SELLER')`).
- **Response (201):** `toListingDto(copy)` — a brand-new `Listing` row with the full standard listing shape (id, title, price, images, status, listingStatus, etc.), **not** the original row.
- **Errors:** `404` not owned/doesn't exist; `409` if original is `draft`; `400` if original has no photos (plus `createListing`'s own validation errors).

## Backend: State-Reset Logic (core finding)

`relistListing` does **not** touch the original listing at all:
1. Reads the original via `findByIdForOwnerWithImages` — no status filter, so callable from `sold`, `inactive`, `reserved`, `approved`, `rejected`, etc. (blocked only for `draft`).
2. Copies a fixed set of content fields into `createListing` — the exact same path a brand-new listing goes through.
3. Returns the **new** row. The original row is never updated or deleted.

This is explicitly intentional, not a bug:
- `listings.controller.ts:97-98` — "the original is untouched."
- `listings.service.ts:1303-1319` — "The original is left exactly as it is: a sold listing keeps its sale history, a paused one stays paused. Nothing is moved or reactivated."
- Test `listings.service.spec.ts:2241-2269` — asserts `updateListingStatusById` and `deleteListing` are **never** called.
- Test `:2286-2296` — confirms relisting a paused listing does not unpause it either.

**Consequences for the sheet's stated behavior:**
- No reset of the original's status to anything, "active" or otherwise.
- "active" status is never produced at all (even on the new copy) — `createListing`'s `publishStatus` is only ever `approved` or `pending_approval` (`listings.service.ts:1001`); `active` is a separate enum value marked "grandfathered" (`schema.prisma:38`) that new/relisted listings never receive.
- **No offer-cancellation / offer-state clearing runs.** `relistListing` never calls `findOpenOffersForListing` or any offer/Stripe service — unlike the sibling `updateListingStatus`, which does cancel open offers on pause/delist.
- There is no `soldAt`/`buyerId` column on `Listing` to clear in the first place — sold state lives in separate `Order`/`OrderItem`/`Offer` tables, all untouched by relist.
- `EP-040`'s own sheet row (`PATCH /listings/:id/status`) implies relist is believed to be the path that takes a sold listing back to active — it is not; relist never changes the sold listing's status at all.

Minor note: `stock` is copied verbatim from the original. Since availability is tracked via the separate `Inventory` model, not `Listing.stock`, this doesn't produce a visibly broken copy, but it's not a deliberate "reset" either — low severity.

## Sheet Check

**Match/Mismatch:** Match (routing/flow), Mismatch (behavioral claim)

- Method/path match exactly: `POST /listings/:id/relist` ↔ `listings.controller.ts:100`.
- **Used in App? = YES:** correct — real call site in mobile `SellerListingDetail.tsx:198`.

- **Endpoint Title's behavioral claim does not match the implementation:**
  - Does not reset the original listing's status at all — explicitly tested as "leaves the original alone."
  - Does not produce an "active" status on anything — relisted listings only ever get `approved` or `pending_approval`.
  - Runs no offer-cancellation / sold-state-clearing logic whatsoever.
  - Both the backend's own code comments/tests and the mobile UI copy ("A new copy ... is live. This listing is unchanged.") consistently describe the opposite of the sheet's claim. This is a deliberately-designed "publish a copy, leave the original alone" behavior — not an accidental bug — but the sheet's test description does not match the implementation, so a test written against the literal title would fail against actual behavior.
