## Declared Contract

- **Params**: none (path, query, header) — matches OpenAPI (`parameters: []`) and controller (`findAll()` takes no arguments).
- **Auth**: none — no guard/decorator on `CategoriesController` or `findAll()` (`categories.controller.ts:6-14`); OpenAPI declares no `security` for this operation either. Agrees.
- **Request body**: none, in both.
- **Response (code)**: raw `Category[]` from Prisma — every schema column: `id, name, slug, icon, image, sortOrder, createdAt, updatedAt` (`categories.repository.ts:17-19`, `schema.prisma:543-558`). No DTO/mapper strips anything (contrast with `getTree()`, which the service explicitly re-maps — `categories.service.ts:42-67`).
- **Response (OpenAPI)**: `200` with empty `description` and **no schema** (`openapi.pretty.json:1215-1219`) — a spec gap; nothing to validate shape, nullability, or required fields against.
- **Error responses**: none declared in code or spec (no explicit error branch in `findAll`/repository call; a DB failure would surface as an unhandled 500 via Nest's default exception filter — not separately documented anywhere).
- **Ordering contract**: `sortOrder asc, name asc` (`categories.repository.ts:17-19`), explicitly called out in the repository's own doc comment and in `docs\features\taxonomy-tree.md:74` as intentional (admin-curated order, BRI-356). Not stated in the OpenAPI summary beyond the human-readable text "in the order the admin set" (`openapi.pretty.json:1213`).

**Conflict/gap:** The sheet title describes this endpoint as the "category tree" with a BA-confirmed "customer-facing" taxonomy filter; neither concept (tree nesting, or any visibility filter) exists in this route's code or schema. Recorded, not resolved.

## Test design inputs

**a. Roles and permissions**
- Public, unauthenticated — no guard on the route (`categories.controller.ts:6-14`), no `security` in OpenAPI. Every role (anon/guest, buyer, seller, admin) gets an identical 200 response; there is no role-based branching anywhere in `findAll`/service/repository.

**b. Ownership rules**
- None apply — `Category` is a shared, non-user-owned resource.

**c. Resource states and visibility rules**
- The `Category` model has no state/status column at all (confirmed absent at `schema.prisma:543-565`) — every row the admin has ever created and not hard-deleted is returned, in `sortOrder, name` order, to every caller, with no draft/inactive/soft-deleted state possible. This is the crux of the sheet-vs-code conflict above.

**d. Validation and error paths**
- No input to validate (no params/body). The only observable error path is an unhandled exception from the Prisma call bubbling to Nest's default error handler (no explicit 4xx path exists for this endpoint); rate-limiting (429) is possible only via the app-wide 100 req/min/IP default (`app.module.ts:57-59`), not specific to this route.

**e. Response contract**
- `id, name, slug, icon, image, sortOrder, createdAt, updatedAt` per category, no nesting, no role/state-dependent fields (since there is no state). OpenAPI declares no schema for this (`openapi.pretty.json:1215-1219`) — a schema-conformance test cannot assert shape against the spec, only against the code's actual Prisma `select`.

**f. Business logic / side effects**
- Read-only, no side effects, no idempotency concerns. Ordering (`sortOrder` then `name`) is the one piece of "business logic," confirmed deliberate via `categories.repository.ts:9-19` and `docs\features\taxonomy-tree.md:74`.

**g. Existing tests and docs**
- Only `categories.service.spec.ts:40-51` (mocked-repository unit tests of `findAll`/empty-array case). No controller-level unit test, no e2e test exercising the real HTTP route was found anywhere under `apps\api\test\` (grepped for `'/categories'` literal — only `/admin/taxonomy/categories` e2e tests exist, a different endpoint). `docs\features\taxonomy-tree.md` and `categories.repository.ts`'s own comments are the only documentation of intent (ordering, legacy-category coexistence).

**h. Fixtures/accounts needed**
- None requiring auth (public endpoint). Useful fixtures for the scenarios below: (a) a seeded DB with the current demographic tree (Women/Men/Kids/Gear) only; (b) a DB state that also includes a legacy/off-tree category still referenced by at least one listing (to probe finding #4/#5); (c) an empty-category DB (no categories at all) to confirm the `[]` response path mobile already unit-tests client-side.

## Summary

- 3 unused/over-exposed response fields: `sortOrder`, `createdAt`, `updatedAt` (never read by the only consumer, mobile).
- 1 unused client-type field: `parentId` (declared on mobile `Category`, never populated — no parent concept exists server-side either).
- 0 dead backend files/branches — all service/repository methods for this route are live.
- 3 conflicts recorded (not resolved): the sheet calls this the "category tree" but it is the flat list (`/categories/tree` is the actual tree, a separate operation); the sheet's "customer-facing" taxonomy-filter claim has no corresponding implementation anywhere in code/schema; legacy off-tree categories can coexist with the curated tree with no exclusion logic (code-comment evidence, not independently confirmed against a live DB).
- 12 suggested test scenarios (see table above).

**Primary finding:** the endpoint is correctly wired, public, and widely used across mobile (10 call sites), but the sheet row's title describes a capability — a "customer-facing" taxonomy filter confirmed with BA — that has no implementation anywhere in this module or its schema, and additionally conflates this flat-list endpoint with the separate tree endpoint. Flagged to QA/PO; not resolved here per instructions.
