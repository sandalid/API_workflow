## Architecture facts established before module analysis

- **No global API prefix.** `apps/api/src/main.ts` never calls `setGlobalPrefix`; Swagger's `addServer('/api')` is documentation metadata only — it does not change the actual mounted routes. Every route in `endpoint-inventory.json` is the real Express-mounted path (e.g. `GET /listings`, not `GET /api/listings`). Mobile's `apiClient.ts` confirms this: `API_URL` (from `EXPO_PUBLIC_API_URL`) is concatenated directly with the service-layer path literal, no `/api` segment inserted.
- **No versioning** (`enableVersioning` not called).
- **Global pipes/filters** (`main.ts`): `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })` with a custom `exceptionFactory` that returns `{ message, error: 'Bad Request', field }` — `field` is the first invalid DTO property, consumed by the mobile sell flow to focus the offending input. `AllExceptionsFilter` is the global exception filter — module analysis must check it for any endpoint whose controller/service doesn't have bespoke exception handling, since it may reshape or swallow error details.
- **Raw-body webhook routes**: `/payments/webhook`, `/payments/webhook/connect`, `/shipping/webhook/shippo` are mounted with `express.raw()` ahead of the global `json()` parser (HMAC/Stripe signature verification needs the exact bytes). Any test scenario against these three routes must send a raw body, not a JSON-serialized one through a client that auto-sets `Content-Type: application/json` the normal way.
- **CORS**: origin allow-list from `CORS_ORIGINS` env, defaults to web (3000) + Expo (8081).
- **Auth guards found**: `JwtAuthGuard`, `OptionalJwtAuthGuard` (`apps/api/src/auth/guards/`), `RolesGuard` + `@Roles(...)` decorator keyed on Prisma `Role` enum plus a literal `'SELLER'` (`apps/api/src/common/decorators/roles.decorator.ts`, `apps/api/src/common/guards/roles.guard.ts`). Per-endpoint analysis must check whether a guard is actually applied at the controller/method level (decorators lie dormant if not applied) and whether `'SELLER'` resolves against `isSeller`/seller-status fields rather than the `Role` enum — this is a likely spot for guard-vs-business-rule mismatches.
- **Database**: `apps/api/prisma/schema.prisma` (2,287 lines), 86 applied migrations under `apps/api/prisma/migrations/`, plus a `prisma/manual-sql/` directory of hand-written guarded SQL patches (money/inventory integrity fixes — e.g. `2026-08-31-repair-leaked-inventory-holds.sql`, `2026-09-01-add-offer-payment-hold-columns.sql`). These manual-sql files are strong evidence of past production incidents in the offer/payment/inventory hold path and should be cross-checked against `docs/ops.md` § Gotchas and `docs/fix/` write-ups where they exist.
- **Mobile API client** (`apps/mobile/src/services/apiClient.ts`): single `request<T>()` chokepoint, 30s default timeout (120s for AI endpoints), distinguishes timeout vs network failure, triggers `authStore.expireSession()` **only** on a 401 for a request that carried a token (anonymous 401s are not treated as session expiry). No blind auto-retry on any verb — this part is accurate and deliberate (mobile's own client-side policy).
- **Idempotency — corrected (2026-11-10 continuation; this overview's original wording was wrong)**: the original text here read "the API has no idempotency keys yet," copied uncritically from `apps/mobile/CLAUDE.md`'s own line 55 ("the API having no idempotency keys yet") without checking source. Reading `apps/api/src/orders/orders.service.ts`, `offers.service.ts`, `payments.service.ts`, `connect.service.ts` directly shows this is **false as a blanket statement**. Two genuinely different things were being conflated:
  - **Stripe-operation idempotency — extensively implemented and tested.** Every money-moving Stripe call carries a deterministic `idempotencyKey`: checkout (`buildCheckoutIdempotencyKey` in `orders.service.ts:87`, keyed on buyer+cart-fingerprint+address+payment-method+a 10s time bucket — `apps/api/CLAUDE.md:54` calls this "Checkout idempotency — closed"), offer holds/re-holds (`buildOfferHoldIdempotencyKey`, `offers.service.ts:121`, same 10s-bucket shape, used at offer-creation, wallet-hold-intent, and counter re-hold), and Connect-side account creation/transfers/reversals/tax-transactions/refunds (`payments.service.ts`, keys like `transfer:${orderId}`, `reversal:${orderId}:${amount}`, `refund:${orderId}:${newTotal}`, `connect-account-create:${userId}`). All of these are asserted by dedicated unit tests (`orders.service.spec.ts:625-646`, `payments.service.spec.ts` — dozens of exact-idempotency-key assertions) — this is a closed, tested concern for the specific operations it covers, not an open gap.
  - **Generic API-request-level idempotency — genuinely absent, and this is the real gap mobile's "no blind auto-retry" policy is compensating for.** There is no `Idempotency-Key` HTTP header, no Nest interceptor/middleware, and no platform-wide request-dedup mechanism (confirmed: zero matches for `Idempotency-Key`/`IdempotencyKey` outside the Stripe-SDK-call-site usages above). Protection against a duplicate HTTP request is therefore **endpoint-specific, not a platform guarantee**: checkout and offer-hold creation are hardened (idempotency key + a DB unique-constraint backstop, e.g. `Order.stripePaymentIntentId @unique`, `Offer.paymentIntentId @unique`, each with a `P2002`-catch), several other mutations are idempotent "by construction" via upsert/no-op-on-existing-state patterns (`UsersRepository.clearPushToken`, `MessagingRepository.createBlock`, `ConnectService.createAccount`/`transferForOrder`, `listings.service.ts`'s unlike), but most endpoints in this inventory have **no documented duplicate-submission protection at all** (e.g. `POST /listings/:id/comments`, `POST /notifications/delete`, `POST /users/:id/report`) — ordinary POST semantics apply, and a double-tap is a real, untested risk precisely because there is no blanket mechanism to catch it.
  - **Per-module implication**: when a module's `business-rules.json`/`test-scenarios.md` addresses duplicate-submission/retry risk, state which of these two idempotency types is in play and cite the specific code (idempotency-key function + DB constraint, or upsert/no-op pattern, or "none found") — never reuse this overview's old blanket phrasing.
- **Mobile mirrors several server-owned state predicates client-side** (documented in `apps/mobile/CLAUDE.md`, with real past-bug IDs): `utils/offerState.ts` (open-offer predicate mirroring `OffersRepository.findOpenForBuyer`), `utils/disputeStatus.ts`, `utils/listingState.ts` (live-listing predicate, note: the buyer-facing DTO flattens `inactive`/`pending_approval`/`rejected` to `available` — only the lifecycle `status` field is authoritative), `utils/sellerState.ts` (seller account status derivation, including a client-only `verifying` status the server never sends). **Every module touching offers/disputes/listings/sellers must check these utils for frontend/backend mismatch candidates** — each has a documented BRI-xxx incident where the mirror drifted from the server rule.
- **Web** (`apps/web/src/app/api/admin/login/route.ts`) has exactly one Next.js-side API route of its own (an admin login proxy/cookie-setting endpoint); everything else in `apps/web/src/lib/api.ts` / `sellerApi.ts` calls the NestJS backend directly, same as mobile.

## Known limitations (updated as analysis proceeds — see `progress.md` and `gaps-and-conflicts.md`)

- Runtime behavior (whether a traced code path actually executes under real conditions) is **never** directly verified — no app was run, no API was called, per task constraints. All "confirmed" language in module docs means "confirmed by reading the code," not "confirmed by execution"; anything that depends on timing, external webhooks, or queue processing is marked pending runtime confirmation.
- Linear is queried per-module by keyword/label, not exhaustively — a ticket that doesn't share obvious vocabulary with its module may be missed. Treat "no related ticket found" as "none found by this search," not "none exists."
- `apps/web`'s own route surface (Next.js pages/Server Components) is traced for *backend API calls*, not audited as its own application.
