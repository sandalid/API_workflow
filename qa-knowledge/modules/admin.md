# Module: Admin

56 endpoints — the largest single controller in the API (`admin.controller.ts`, 566 lines; `admin.service.ts`, 828 lines; `admin.repository.ts`, 659 lines; plus `taxonomy.service.ts`/`taxonomy.repository.ts`, ~18KB combined, and 25 DTO files). Web-only by design and by confirmed fact (zero mobile references found by grep; `apps/web/src/lib/api.ts` references `admin/` 70 times across its 573 lines).

Analyzed against commit `91e0447b`. Depth is intentionally uneven across the 56 routes, as the original analysis brief allowed: every money-moving, destructive, or privilege-sensitive endpoint was read down to the service-method body; simple list/CRUD endpoints were read at the controller+DTO level (enough to confirm guard, params, and documented behavior) without independently re-tracing every repository query. Endpoints given the lighter pass are marked `partial` in `endpoint-inventory.json` with a one-line reason, per instruction — not silently downgraded.

## Guard — uniform across all 56 routes, verified directly, no exceptions found

`@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles(Role.ADMIN)` at **class level** on `AdminController` — every single route requires the real Prisma `Role.ADMIN` enum value (not the `'SELLER'` pseudo-role used elsewhere in the API). No per-route guard override exists anywhere in the 566-line controller — confirmed by reading the file in full, not sampling. This is the one controller in the whole codebase where "is the guard actually applied, not just named suggestively" (the task's own standing instruction) has a simple, clean, fully-affirmative answer.

## Known admin-surface fragmentation (confirmed, not this module's bug to fix)

The `admin/*` URL prefix is **not exclusively owned by this controller** — four other controllers mount routes under the same prefix: `admin/dispute-cases*` + `admin/dispute-cases/:id/approve|deny` live in `disputes.controller.ts` (separate, newer arbitration console — see `modules/disputes.md`'s own cross-reference, which names `BRI-556` as the open question about whether this controller's older `admin/disputes`/`admin/orders/:id/resolve-dispute` should still exist alongside it); `admin/conversations*`, `admin/messages/flagged`, `admin/conversation-reports*`, `admin/users/:id/chat-ban` live in `messaging.admin.controller.ts`; `admin/reviews`, `admin/product-reviews` live in `reviews.controller.ts`; `admin/feed/*` lives in `feed/curation.controller.ts`. None of those routes are analyzed in this document — flagged here only so a reader of this module doesn't assume the admin surface is fully enumerated by these 56 routes alone.

## Stats & dashboards

- **`GET /admin/stats`** — overall platform statistics. Read at controller/DTO level only (`partial` — no query params, straightforward aggregate read, lowest-risk route in the module).
- **`GET /admin/orders/chart`** — order volume over time, `groupBy` parameter (exact allowed values not independently re-verified against `GetAdminOrderChartQueryDto` in this pass — `partial`).
- **`GET /admin/shipping-reconciliation`** — diffs each order's actual carrier cost (`Shipment.costAmount`, summed across outbound/return legs) against the buyer's flat `shippingTotal`. **Only includes orders with at least one cost-tracked shipment leg** — `costAmount` is nullable and explicitly **not backfilled for older rows** (confirmed directly in the route's own `@ApiOperation description`), so an older order can be silently absent from this report even if it had real shipping costs. Worth a boundary test using a pre-cost-tracking-era order fixture, if one can be constructed, to confirm the documented exclusion rather than an error.

## Orders

- **`GET /admin/orders`**, **`GET /admin/orders/:id`** — list/detail, `partial` (standard paginated/filtered reads, not independently re-traced against `orders.repository.ts`).
- **`PATCH /admin/orders/:id`** (`updateOrderStatus`) — delegates straight to `OrdersService.applyAdminStatusChange(id, dto, adminId)`, the **same shared method** `resolveDispute`/`issueRefund`/`retryPayoutReversal` all funnel through below — this is the module's one central order-mutation chokepoint, not four independent code paths. `UpdateOrderStatusDto`: `status` (required, `@IsEnum(OrderStatus)` — the full Prisma enum, not a restricted admin-allowed subset at the DTO layer; any state-machine restriction, if one exists, lives inside `applyAdminStatusChange` itself — cross-reference `modules/orders.md` during consolidation, not re-derived here), plus optional `trackingNumber`/`trackingUrl`/`estimatedDeliveryDate`/`estimatedDeliveryTime`. The admin's own id is threaded through specifically so the order's status-history timeline records *who* made the change (`changedById`), confirmed directly in the controller's own comment.

## Listings

- **`GET /admin/listings`** — paginated, filterable by `status`/`q`/`categoryId`/`brandId`/`condition` (`partial`, straightforward read).
- **`PATCH /admin/listings/:id/status`** (`updateListingStatus`) — the one listing-mutation route in this module, and it does more than a bare status flip: reads the **old** status first, writes the new one, then (1) invalidates the listing's read-through cache (`listings.invalidateCache`, the same cache `docs/architecture.md` names as `listing:${id}`) and (2) syncs the embedding index for the old→new status transition (`listings.syncEmbeddingIndex`) — so an admin-driven status change correctly participates in both the cache layer and the search-embedding pipeline, not just the DB row. A plain Prisma "not found" (`P2025`) is deliberately the *only* error code mapped to a 404 (`isNotFoundError`, a small static helper reused across several methods in this service) — any other DB error is left to bubble to the global exception filter as a 500 rather than being misreported as "not found."

## Users

- **`GET /admin/users`** (`getUsers`) — `status` param selects **two slices, not three**, despite the domain itself modeling three deletion states: `active` (default) or `deleted`. The `deleted` slice covers **both** a still-restorable account (`deletionState: pending_deletion`) and an already-purged one (`deletionState: deleted`) — and the two carry genuinely **different row shapes**, confirmed directly in the service's own extensive doc comment: a purged account's identity is read from a separate `deletionArchive` table (`toDeletedAccountRow`), never from the scrubbed live user row, specifically because rendering the scrubbed row for a purged account would show an indistinguishable "Deleted user" for every purged row with no way to tell them apart. **A test iterating the `deleted` slice must handle two different response shapes, not one.**
- **`POST /admin/users`** (`createUser`) — admin-initiated account creation: checks for a duplicate email first (`findByEmail`, 409 implied on match, not independently re-verified exact status in this pass), **generates a random password server-side**, creates the user, emails them the credentials, and **returns the generated password in the response** so the admin can optionally share it through a second channel. This is a deliberate design choice, not a leak — the recipient is the calling admin, who is expected to be the one distributing it — but it means a test fixture creating a user this way receives a real, usable password in the HTTP response body; per this task's "never include credentials...in the output" constraint, do **not** paste an actual generated password into any committed test-scenario example, reference it structurally only ("the response includes a generated password field").
- **`GET /admin/users/:id`** (`getUserById`) — full detail: identity, signup preferences, buyer-side spend total, latest orders, **and the user's Data Export History** (confirmed by reading the method — `dataExport.getHistory(id)` is fetched in the same `Promise.all` as the user row and spend total). Deliberately shaped to match `getSellerById`'s shape "so the two admin detail pages render alike," per the method's own comment.
- **`PATCH /admin/users/:id/suspend`** (`suspendUser`) — simple boolean flip (`SuspendUserDto.suspended: boolean`), 404 on a not-found user via the same `isNotFoundError` helper. Not independently traced into what a suspended flag actually *blocks* elsewhere in the API (login? order creation? — cross-reference `auth`/`orders` modules during consolidation rather than assuming).
- **`POST /admin/users/:id/restore`** (`restoreUser`) — "For the support case self-service cannot cover — a user locked out of the account they asked to delete," per the route's own description. Three-way branch, all independently confirmed by reading the method: already-purged (`deletedAt` set) → `409` ("already been permanently deleted and cannot be restored"); not actually scheduled for deletion (`deletionScheduledFor` null) → `409` ("not scheduled for deletion"); otherwise → calls `AccountDeletionService.cancelDeletion` (cross-reference the `users` module's own deletion-request/confirm flow, already analyzed, for the full state machine this cancels). **Two distinct 409 scenarios with different messages** worth two distinct test cases, not one generic "already handled" assertion.
- **`POST /admin/users/:id/export-data`** (`requestDataExport`) — **asynchronous by design**: creates a pending history row and returns `202 Accepted` immediately; the actual gather/zip/email work happens in a worker process, confirmed by both the `@HttpCode(HttpStatus.ACCEPTED)` decorator and the route's own description ("the response returns immediately, before the export is ready"). A test must poll `GET /admin/users/:id`'s embedded Data Export History to observe completion — the 202 response itself carries no completion signal, same "accepted into a queue, not completed" shape documented for `POST /embeddings/reconcile` in `modules/embeddings.md`.
- **`PATCH /admin/users/:id/role`** (`updateUserRole`) — `UpdateUserRoleDto.role: @IsEnum(Role)`, i.e. the full two-value Prisma `Role` enum (`USER`/`ADMIN` — per `overview.md`'s architecture notes, there is no three-tier role system). **This endpoint can promote any user to `ADMIN`**, which — combined with this controller's class-level `@Roles(Role.ADMIN)` guard — means any existing admin can mint new admins with no additional confirmation step visible in this code path. Flag as the single highest-privilege-escalation-risk endpoint in this module for test prioritization: verify it truly requires an existing admin caller (not merely any authenticated user), and consider whether a product-level control (e.g. requiring 2FA, a second-admin approval, or an audit-log entry) exists elsewhere for this specific action — not found in this controller/service, so either it lives elsewhere (unconfirmed) or is a genuine gap.

## Sellers

- **`GET /admin/sellers`**, **`GET /admin/sellers/:id`** — list/detail (`partial`, standard paginated reads).
- **`PATCH /admin/sellers/:id/clear-phone-2fa`** (`clearSellerPhone2fa`, `BRI-340`) — bypasses Seller Hub's payout-change 2FA gate for exactly **15 minutes** (a hardcoded `Date.now() + 15*60*1000` window, not configurable), for a seller who has lost access to their verified phone number. The route's own description names the real-world support scenario directly. 404 via the same `isNotFoundError` helper (mapped to "Seller not found"). A concrete, testable boundary: confirm the override genuinely expires after 15 minutes and doesn't silently extend on repeated reads.

## Promotions (admin side — contrast with the public `POST /promotions/validate` in `modules/promotions.md`)

- **`GET /admin/promotions`**, **`POST /admin/promotions`**, **`DELETE /admin/promotions/:id`** — straightforward CRUD against the same `Promotion` model `modules/promotions.md` already documents the public validate-side behavior for (case-sensitive-uppercase matching, no usage-tracking). Not independently re-verified here whether `createPromotion` enforces uppercase `code` storage — **this is the exact cross-check `modules/promotions.md` flagged as needed**, and it was not performed in this pass either (`partial` — confirm during a future consolidation pass by reading `AdminService.createPromotion`'s body directly).

## Taxonomy — categories (admin.service.ts) vs. subcategories/types/attributes (taxonomy.service.ts): two different services, confirmed

- **`GET/POST/PATCH /admin/taxonomy/categories`[`/:id`]** — standard CRUD via `AdminService`. **`deleteCategory` is referentially guarded**: counts listings in the category first; **409 if any exist**, naming the exact count and instructing the admin to move them first (exact message read directly from source). Renaming is explicitly safe per the route's own description, since listings reference a category by id, not name.
- **`GET /admin/taxonomy/tree`** — the full 3-level tree via `TaxonomyService.getTree()` (the admin-facing twin of the public `GET /categories/tree` documented in `modules/categories.md` — not independently re-verified whether the two share the same underlying query or are two separate implementations; flag for cross-check, same shape as the promotions code-casing flag above).
- **`POST /admin/taxonomy/categories/:categoryId/subcategories`** (`createSubcategory`) — 404 if the parent category doesn't exist; **a child's parent is always a path segment, never a body field** — the controller's own section comment states this explicitly as deliberate design: "That is what makes an orphan unrepresentable rather than merely rejected — there is no shape of request that creates a subcategory without naming a category." Image is required (`BRI-356`).
- **`DELETE /admin/taxonomy/subcategories/:id`** (`deleteSubcategory`) — **cascades to its types unconditionally**, confirmed directly in the service method (`repo.deleteSubcategory(id)` after a 404 check, response reports `deletedTypes: existing._count.types`). **No listing-reference check exists for this delete** — contrast directly with `deleteCategory`/`deleteBrand`, both of which block on listing references. This is a real, source-confirmed asymmetry: deleting a category or brand that listings reference is refused; deleting a subcategory (or, per the next finding, a type) that listings reference is **not** — worth its own explicit test and its own `gaps-and-conflicts.md` entry, since it's unclear whether this is intentional (maybe listings reference the type, not the subcategory, making a subcategory-level orphan harmless) or an oversight. Not resolved either way in this pass.
- **`DELETE /admin/taxonomy/types/:id`** (`deleteType`) — same shape: 404-then-delete, **no listing-reference check found** either. If listings store a `typeId` foreign key (plausible, not independently confirmed against the Prisma schema in this pass), this could orphan listings in a way `deleteCategory`/`deleteBrand` were specifically built to prevent. Flag as the single most concrete "same safety pattern applied inconsistently across sibling resources" finding in this module.
- **Filter attributes** (`GET/POST/PATCH/DELETE /admin/taxonomy/attributes`) — `createFilterAttribute`/`updateFilterAttribute` **re-validate that named subcategory/type targets still exist server-side at save time**, per the route's own description, "since one can be deleted between the picker loading and the save" — a real TOCTOU (time-of-check-to-time-of-use) consideration worth a concurrency test (create an attribute targeting a subcategory, delete that subcategory in a separate request, confirm the attribute's own data doesn't silently point at a ghost id — not independently verified what happens to an *existing* attribute's targets when the thing they point to is deleted after the attribute was saved, only that *creating/updating* re-checks). `updateFilterAttribute`'s `values`/`targets` fields are **wholesale-replace semantics, not merge** — sending either field replaces that whole set; omitting a field leaves it untouched (confirmed directly in the route's own description).

## Taxonomy — brands

- **`GET/POST/PATCH /admin/taxonomy/brands`[`/:id`]** — standard CRUD.
- **`DELETE /admin/taxonomy/brands/:id`** (`deleteBrand`) — same listing-reference-count guard as `deleteCategory` (409 naming the count), but the route's own description calls out **why this guard matters more here than for categories**: `Listing.brandId` is **nullable** at the database level, so "unlike a category the database would NOT stop this" — the application-level count check is the *only* thing preventing a brand delete from silently orphaning (nulling) every listing's brand reference. This is a materially different risk profile from `deleteCategory` (where a DB-level FK constraint would likely also catch a careless delete) and worth noting as such in any test-prioritization: the brand-delete guard is load-bearing in a way the category-delete guard might only be reinforcing.

## Taxonomy — materials (`BRI-811`, the admin write-side of `modules/materials.md`'s public read endpoint)

- **`POST /admin/taxonomy/materials`** (`createMaterial`) — name is normalized (`normalizeMaterialName`, exact normalization rule — likely case/whitespace folding, not independently re-derived from source in this pass) before a slug is generated and the row is appended at the current max sort order. **409 if a material with the same normalized name already exists** ("ignoring case and spacing," per the route's own description) — confirmed via a `materialConflict(err, name)` error-mapping helper wrapping the create call.
- **`PUT /admin/taxonomy/materials/order`** (`reorderMaterials`) — **all-or-nothing optimistic-concurrency guard, read directly from source and confirmed precisely**: the submitted `ids` array must be **exactly** the current full set of material ids (same length, same members) — a stale client (one that loaded the list before another admin added/removed a material in a separate tab) is refused outright with a 409 ("The materials list changed since you loaded it. Reload and try again."), **never partially applied**. This is a clean, well-designed concurrency control worth a dedicated test: submit a reorder with one id missing/extra and confirm the whole operation is rejected, not silently truncated.
- **`PATCH /admin/taxonomy/materials/:id`** (`updateMaterial`) — rename only; **existing listings keep whatever material text they were published with** (free text per `modules/materials.md`'s own finding — renaming the admin-curated option has zero retroactive effect on already-created listings), confirmed directly by both the route's own description and the service method (no listing-row update anywhere in `updateMaterial`).
- **`DELETE /admin/taxonomy/materials/:id`** (`deleteMaterial`) — **no listing-reference check at all** (plain 404-then-delete) — consistent with, and explained by, the free-text nature of `Listing.material`: there is nothing to orphan, since no listing row stores a foreign key to this table in the first place. This is the one taxonomy-delete-without-a-reference-guard that is clearly *correct* by design (contrast with the unresolved `deleteSubcategory`/`deleteType` finding above, which may or may not be correct for the same reason — not confirmed either way for those two).

## Platform settings

- **`GET /admin/platform-settings`** — commission rate (basis points, 1000 = 10.00%) and a high-value threshold (cents), with a change-log history. Both settings apply **only at listing creation/relist**, or — threshold only — **on a price edit**, **never retroactively** to an existing listing's already-locked-in rate, per the route's own description. This directly corroborates `modules/offers.md`'s own finding that `sellerPayoutCents` is computed off "the listing's locked-in `commissionRateBps`" — the two documents independently confirm the same non-retroactive-commission design from opposite ends (admin-write side here, offer-payout-read side there).
- **`PATCH /admin/platform-settings`** — **only fields actually changing get a new change-log row** — saving with an unchanged value is a documented no-op, not a redundant audit entry. Not independently re-verified at the `PlatformSettingsService` level (this route delegates to a separate module, `platform-settings`, not itself part of the 31-module inventory this knowledge base enumerates as a route-bearing module — it has no controller of its own, confirmed earlier in `overview.md`'s architecture survey of which `src/` directories lack a controller).

## Disputes & refunds — the module's highest-risk money-moving cluster

- **`GET /admin/disputes`**, **`GET /admin/refunds`**, **`GET /admin/stripe-chargebacks`** — read-only lists (`partial`).
- **`POST /admin/orders/:id/resolve-dispute`** (`resolveDispute`) — `ResolveDisputeDto.resolution`: `'RELEASE_TO_SELLER' | 'REFUND_BUYER'` (`@IsIn`), optional `amount` (integer cents, `@Min(1)`, omit for full remaining balance). **`RELEASE_TO_SELLER` moves no money** — the seller's payout already stands, so this branch is a pure order-status flip to `delivered`. **`REFUND_BUYER`** calls `ConnectService.refundOrder(orderId, amount)` **first** — which, per this method's own doc comment, reverses the seller's Stripe transfer if it already went out, *then* refunds the buyer's charge — and the order is only marked `cancelled` **after** Stripe confirms the refund succeeded, never the reverse order. A `null` result from `refundOrder` (nothing to refund — no successful payment found, or already fully refunded) is a clean `BadRequestException`, not a silent no-op or a 500. **Both branches land through `OrdersService.applyAdminStatusChange`** (the same shared chokepoint `updateOrderStatus` uses), specifically — per the method's own comment — so the order timeline row is written and the inventory hold is released, rather than a bare repository status write that would skip both.
- **`POST /admin/orders/:id/issue-refund`** (`issueRefund`) — `IssueRefundDto`: just the optional `amount`. Functionally **a strict subset of `resolveDispute`'s `REFUND_BUYER` branch** — same `refundOrder` call, same null-check, same terminal `cancelled` status via `applyAdminStatusChange`. The two endpoints exist separately because they're reached from different admin UI contexts (an active dispute vs. a refund issued without one), not because the underlying mechanics differ — confirmed by reading both method bodies side by side.
- **`POST /admin/payouts/:orderId/retry-reversal`** (`retryPayoutReversal`) — the most tightly-gated of the three money-moving routes: first confirms a `Payout` row exists for the order **and its status is literally `reversal_failed`** (400 otherwise, "nothing to retry") — then calls the exact same `refundOrder` path, now explicitly widened (per the method's own comment) to also accept a payout already in `reversal_failed` state, not just `transferred`. A successful retry **both** re-attempts the Stripe transfer reversal **and** refunds the buyer in one call, "inheriting the `payoutHeld` guard for free" rather than a bespoke reversal code path, per the comment. This is manual recovery tooling for a specific, named failure mode (a seller's connected-account balance couldn't cover the reversal at the time it was first attempted) — a test fixture for this endpoint needs a `Payout` row genuinely in `reversal_failed` state, which is not independently creatable via any other endpoint in this knowledge base so far (cross-reference `connect`/`payments` modules during consolidation for whether a fixture path exists, or whether this must be noted as a real test-setup blocker).
- **`POST /admin/stripe-chargebacks/:id/write-off` (`writeOffChargeback`)** — **audit-trail only, does not release the payout hold**, per the route's own `@ApiOperation` description (a materially important distinction for a tester: this does NOT move money or change payout state, despite sitting in the same money-adjacent cluster as the three routes above). Guarded precisely: 404 if the `StripeDispute` doesn't exist; 400 if `writtenOffAt` is already set (no double-write-off); 400 if `status` is anything other than `'lost'` or `'warning_closed'` (the exact two terminal-loss states, named in the error message when rejected) — a `won`/`needs_response`/other-status chargeback cannot be written off through this route.

## Authenticity

- **`GET /admin/authenticity`** (`getAuthenticityQueue`) — a concrete, source-confirmed business rule for queue membership: every **non-deleted** listing where **either** `status === 'pending_approval'` **or** `price >= 10000` (i.e. **$100.00 or higher**, in cents) — confirmed by reading the repository query directly (`NOT_DELETED` spread + an `OR` on exactly those two conditions). A listing can enter this queue purely by price, regardless of its approval status — worth a boundary test exactly at the $99.99/$100.00 line.

## Offers (admin)

- **`GET /admin/offers`** (`getAllOffers`) — a **separate, admin-only read surface** over the same `Offer` model `modules/offers.md`'s 8 buyer/seller-facing endpoints already analyze in depth — explicitly flagged as out-of-scope-but-noted in that document already (cross-reference confirmed bidirectionally). Default page size here is **50**, not the 20 used by most other paginated admin lists in this module (not independently verified as a deliberate choice vs. an inconsistency — flag, don't assert). Response rows are manually shaped (listing title/image/price, buyer/seller usernames, amount, status) directly in the service rather than through a shared DTO mapper — several fields read via `as any` casts on the Prisma result (`(o as any).listing?.title`), which is a **type-safety gap worth noting** (not a runtime behavior gap — the casts don't change what data is returned, just that TypeScript isn't verifying the shape at compile time).

## Business-rule-relevant findings for consolidation

- **BR-ADMIN-001**: every route in this controller requires the real `ADMIN` role, verified uniformly, no exceptions.
- **BR-ADMIN-002**: `updateOrderStatus`, `resolveDispute`, `issueRefund`, and `retryPayoutReversal` all converge on the same two shared chokepoints (`OrdersService.applyAdminStatusChange` for status/timeline/inventory-release; `ConnectService.refundOrder` for the actual money movement) — these four endpoints are not four independent implementations and a fix/regression in either shared method affects all of them simultaneously.
- **BR-ADMIN-003 (asymmetric referential-integrity guards)**: `deleteCategory`/`deleteBrand` block on live listing references (409 + count); `deleteSubcategory`/`deleteType` do not (cascading delete with no check); `deleteMaterial` correctly has no check (free-text field, nothing to orphan). The subcategory/type gap is flagged as unresolved — may be intentional, may not be.
- **BR-ADMIN-004**: `PATCH /admin/users/:id/role` can promote any user straight to `ADMIN` with no additional confirmation step visible in this controller/service — the single highest-risk endpoint in this module for a privilege-escalation-focused test pass.
- **BR-ADMIN-005**: `POST /admin/users/:id/export-data` and the embeddings module's `POST /embeddings/reconcile` share the identical "202/200-accepted-but-not-completed, verify via a separate read" contract shape — worth a single consolidated async-completion test pattern rather than two bespoke ones.
- **Unresolved, flagged honestly**: whether `createPromotion` enforces uppercase code storage (cross-reference with `modules/promotions.md`'s matching open question) and whether `admin/taxonomy/tree` shares an implementation with the public `GET /categories/tree` were both left unconfirmed in this pass — note for a future deeper read rather than guessing either way.
