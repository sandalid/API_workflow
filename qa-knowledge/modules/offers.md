## Prior-incident evidence (per the task's lead) — now fully traced

The four manual-sql files are the paper trail of **one real production incident**, and the current code is the fixed state, not the broken one:

1. `2026-09-01-add-offer-payment-hold-columns.sql` — additive columns for `paymentIntentId`/`paymentMethodId` (Epic 4 build-out, not itself a fix).
2. `2026-09-03-add-offer-payment-intent-unique.sql` — a `@unique` index on `Offer.paymentIntentId` because "the same wallet-confirmed PaymentIntent could back two different Offer rows — nothing enforced single-use."
3. `2026-09-05-add-offer-accepted-unique-index.sql` — a **hand-written partial unique index** `Offer_listingId_accepted_unique ON "Offer"("listingId") WHERE status = 'accepted'`, because Prisma's schema DSL can't express a WHERE-qualified unique index. This is the real backstop for "at most one accepted offer per listing" — the in-service check in `acceptOffer` (`findUnpaidForListing` + `some(status === 'accepted')`) is explicitly documented in its own comment as "a race-narrowing check, not a guarantee."
4. `2026-09-07-resolve-duplicate-accepted-offer.sql` — a **data repair** for a real pre-existing violation found when migration #3 was auto-deployed by CD and failed with Prisma `P3018`: two `accepted` rows on listing `cmpnmj7ep0001terjgfmmxme6`, 12 minutes apart, same buyer/seller/amount. One had no order and no payment hold (a dead end, root-caused to `closeSiblingOffers` only ever closing `pending`/`countered` siblings, never an already-`accepted` one — exactly the gap `BRI-280` was filed against); the other had completed a real checkout. Resolved by setting the dead row to `cancelled`.
5. `docs/fix/rca-2026-09-07-offer-accepted-duplicate-deploy-block.md` is the RCA for the **deploy-pipeline** symptom (CD blocked, not a user-facing outage) — root-caused to a migration marked "NOT YET APPLIED… needs a human/product decision" in its own header being merged into `development` and auto-deployed anyway, with no CI check for that marker. Flagged, not fixed, as a process gap.

**Current state, verified by reading `acceptOffer` end-to-end (`offers.service.ts:904-1192`):** the race is now closed at three layers —
- **Application check**: `findUnpaidForListing(offer.listingId).some(o => o.id !== offerId && o.status === 'accepted')` → `ConflictException` before any Stripe call.
- **DB constraint**: the partial unique index on `(listingId) WHERE status='accepted'` — a concurrent accept that slips past the application check hits a Prisma `P2002` on `updateStatus`.
- **Compensation on P2002**: the losing request's own capture (which already succeeded, since capture happens *before* any DB write) is refunded (`refundCapturedOfferPaymentIntent`), its own just-created Order is cancelled, the buyer is notified ("accepted by another buyer moments before yours went through… refunded in full"), and the same `ConflictException` message is re-thrown so the caller sees an identical error whether the race was caught early or late.

This closes the original incident class. **What remains open** (see `offers.gaps.md`): `BRI-297` (capture-failure retry per the client's confirmed "20a" decision — 15-min retry then clean cancel — is **not implemented**; the current code throws immediately on a failed capture with no retry) and `BRI-535` (expiry is still read-time only, no scheduled sweep, confirmed still Backlog in Linear).

## Endpoint-by-endpoint

### 1. `GET /offers` (`offers.controller.ts:18-24`)

- **Guard**: class-level `@UseGuards(JwtAuthGuard)` — no per-route override, so every route in this controller requires a bearer token. No `RolesGuard`/`@Roles` — any authenticated user (buyer or seller role is not a Prisma `Role`, it's the `isSeller` pseudo-role, irrelevant here since offers work symmetrically for both directions).
- **DTO**: `GetOffersQueryDto` — `direction?: 'incoming' | 'outgoing'`, `@IsEnum` validated, optional (omitting it returns both).
- **Service**: `OffersService.getOffers(userId, direction)` (`:778-795`). Does two side-effecting sweeps **before** the actual read, both best-effort (never throw):
  1. `findStaleWithHoldsForUser` → for each still-open-but-expired offer carrying a live hold, `stripe.cancelOfferPaymentIntent` (release the hold).
  2. `expireStaleAndNotify` → `findStaleForUser`, then per-offer `expireOne` (an `updateMany` scoped to `status IN (pending,countered)` as its own concurrency guard — returns `count===1` only for whichever caller's write actually lands first) and a best-effort notification to whoever was left waiting.
  Then `repo.findByUser(userId, direction)` and maps each row through `toDto`.
- **Why this endpoint carries expiry-settling logic**: there is **no `GET /offers/:id`** — the client derives all offer detail (including the `OfferThread` detail screen) from this one list endpoint's rows. That is why expiry is settled here rather than, say, on accept/decline — this is the only read path that exists.
- **Response shape (`toDto`, `:304-383`)**: includes computed fields no column stores — `direction` (`buyerId === requesterId ? 'outgoing' : 'incoming'`), `awaitingFrom` (`'seller' | 'buyer' | null`, derived from `nextResponderId`, added for BRI-248), `countersRemaining` (added for BRI-357, `MAX_COUNTERS_PER_PARTY - countersBy(...)`), `closeReason` (added for BRI-366, read off the closing history entry), `sellerPayoutCents` (listing's locked-in `commissionRateBps`, BRI-602), `cardBrand`/`cardLast4` (BRI-816 snapshot). All of these exist specifically to stop a client re-deriving a server rule and drifting from it — see the BRI-248/252/357 fix docs.
- **No pagination** — `findByUser` returns the full set ordered by `createdAt desc`, no `skip`/`take`. For a buyer/seller with a very long offer history this is an unbounded read; not flagged as broken (no evidence of a reported issue), but worth a load-shape test since `docs/architecture.md`'s stated invariant is "pagination on list endpoints."

### 2. `POST /offers` (`:27-34`) — `createOffer`

Full precondition chain, in order (each one is a distinct failure mode worth its own test case):
1. Listing must exist (`NotFoundException`).
2. `assertOfferable(listing.status)` — status must be `approved` or `active` (`OFFERABLE_STATUSES`). **Deliberately narrower than checkout's `active | approved | reserved`** — `reserved` means a sale is pending and the buyer's product page already hides Make Offer there. 409 Conflict, generic message (buyer is never told *why* — paused vs. in-review vs. rejected are indistinguishable from this error).
3. Seller-leaving check (`findIdsWithSellerLeaving`) — same 409, same generic message (BRI-375).
4. `listing.negotiable` must be true — 400. (Per `docs/domain.md`, every listing is negotiable by default now; BRI-499 removed the seller-facing toggle, but the column/check still exist as a safety net.)
5. **Self-dealing**: `listing.sellerId === buyerId` → 400 (see table above).
6. `validateOfferBounds` — amount `<= listing.price` (equal-to-list allowed, per `BRI-54` Business Rule 1's resolved "not more than" reading) and `>= resolveOfferFloorCents(listing.price, listing.minOfferPercent)` (seller-set floor, 50% platform fallback — BRI-38).
7. Buyer must have a Stripe customer (`getUserStripeInfo`) — 400 if not.
8. Exactly one of `paymentMethodId` (card) / `walletPaymentIntentId` (pre-confirmed wallet hold) is expected:
   - **Card path**: `paymentMethods.findById` must exist, belong to `buyerId`, not be expired (`isCardExpired`), and be a supported brand (`isSupportedCardBrand`, BRI-238 — UnionPay etc. rejected). No `paymentMethodId` at all → 400 ("Add a valid payment method before making an offer.").
   - **Wallet path**: the hold is independently verified against Stripe (`retrievePaymentIntentStatus`) — must be `requires_capture`, must belong to this buyer's Stripe customer, and its derived tax component (`pi.amount - amountCents - shipping`) must be `>= 0` and under `MAX_REASONABLE_OFFER_TAX_RATE` (20%) of the offer amount. This specifically defends against replaying a confirmed wallet hold id from a different (cheaper) listing/amount against a higher offer.
9. Buyer must have at least one saved address (`addresses.findAll`) — 400 (BRI-234: an accepted offer becomes a shippable order with no further address-collection step, so this has to be enforced here, not just client-side).
10. **One active offer per buyer per listing** — `findOpenForBuyer` (open status + unexpired) — 400 if one exists (BRI-54).
11. Hold creation: card path creates a fresh manual-capture PaymentIntent for `amount + shipping + realStripeTax`, idempotency-keyed (`buildOfferHoldIdempotencyKey`, 10s window) so a client retry within the window reuses the same PaymentIntent rather than placing a second hold.
12. `repo.create` — catches Prisma `P2002` on the `@unique paymentIntentId` and rethrows as a 400 ("This payment hold has already been used for another offer.") rather than a raw constraint error leaking out.
13. Best-effort seller notification (push + email) — failures logged, never thrown.

**Money math**: integer cents throughout. Hold total = `amountCents + listing.shippingPrice + realStripeTax(card path)` or the already-authorized wallet amount. `shippingCents` and `taxCents` are **snapshotted onto the Offer row at creation** and never re-read from the listing afterward (BRI-460) — this is what keeps a counter's re-hold and the eventual accept's capture internally consistent even if the listing's shipping tier changes mid-negotiation.

**No explicit inventory hold at offer-creation time.** An open offer places a Stripe payment hold, not an inventory commit — `assertStillAvailable` (used by accept/counter) reads live `onHand - committed - unavailable`, which an open-but-unaccepted offer never touches. Inventory is only committed at `acceptOffer`'s `incrementCommitted` call, after capture succeeds.

> **Correction (2026-11-10 continuation) — resolving an internal contradiction flagged on review.** This section and the step-5/item-3 note below (`"assertStillAvailable does not catch this: acceptance commits no inventory"`) read as contradictory on a first pass — one says accept commits inventory, the other says it doesn't. Re-read directly against `offers.service.ts` (lines 904-936, 1120-1127):
>
> - **Inventory commit does happen on every successful accept, unconditionally** — `inventory.incrementCommitted(offer.listingId, 1)` at `offers.service.ts:1124`, the second-to-last step of `acceptOffer` (after capture, order creation, payment confirmation, and the status flip to `accepted` all already succeeded). This is not in question; there is exactly one call site and it is on the accept path only.
> - **The "acceptance commits no inventory" comment** (`offers.service.ts:921`, verbatim in the source, not a paraphrase) is about a narrower claim: the race window **between two concurrent `acceptOffer` calls for two different offers on the same listing**. `assertStillAvailable` is checked early in the method (line 936), well before the capture/order-creation/`incrementCommitted` sequence that follows it in the same call. If two accept calls for offer A and offer B interleave, call B can reach its own `assertStillAvailable` check *before* call A has reached its own `incrementCommitted` — at that instant `committed` genuinely has not moved yet, so B's availability read is correctly reported as `> 0`, and B proceeds. The comment is explaining why `assertStillAvailable` alone is insufficient as the race-closing check — not claiming inventory is never committed by acceptance in general. This is exactly why the method also has the separate `findUnpaidForListing`(status=`accepted`) application check immediately before it, plus the DB-level partial unique index (`Offer_listingId_accepted_unique`) as the final backstop — three independent layers for one race, because none of the first two closes it alone.
> - **Net, source-verified answer to "does offer acceptance commit inventory, at what step, under what conditions":** Yes, on every successful (non-raced, non-failed) accept, at `offers.service.ts:1124`, as step 12 of 15 in `acceptOffer`'s sequence — conditioned on the hold having been successfully captured (step 6) and the order successfully created (step 8) first; if either of those fails, the method refunds/rolls back and `incrementCommitted` is never reached. The "commits no inventory" phrasing lower in this document refers only to the instant *before* that step, within the same call, relative to a concurrent sibling accept — not to the accept flow's end state.

### 3. `POST /offers/preview` (`:37-44`) — `previewOfferTotal`

Read-only, no state created. Listing must exist; if the buyer has no address, returns `{ shippingCents, taxCents: 0, totalCents: amountCents + shippingCents }` rather than guessing a jurisdiction (same shape as `OrdersService.preview()`). Otherwise calls `calculateOfferTax` (real Stripe Tax) against the buyer's first/default address. Shares `calculateOfferTax` with `createOffer`'s card path and `createWalletHoldIntent`, so the number shown here is guaranteed to match what a subsequent hold actually authorizes for — this is the whole point of the endpoint (BRI-363).

### 4. `POST /offers/wallet-hold-intent` (`:47-54`) — `createWalletHoldIntent`

Step 1 of the Apple Pay/Google Pay flow (Epic 5). Runs the same preconditions as `createOffer` up through the address/bounds checks **except it never checks `assertOfferable(listing.status)` or the seller-leaving check** — confirmed by reading the method body (`:603-630`): it validates listing existence, `negotiable`, self-dealing, offer bounds, and the buyer's Stripe customer, then calls `previewOfferTotal` and creates an **unconfirmed** manual-capture PaymentIntent via `createUnconfirmedOfferHoldPaymentIntent`. **This is `BRI-588`'s exact documented gap** (open, Backlog in Linear): a wallet hold can be authorized for a paused/in-review listing even though the subsequent `createOffer` call will refuse to actually place the offer — the buyer is left with an authorized-but-orphaned hold if they abandon Review Offer after authorizing. No Offer row is created at this step (deliberately — a cancelled/failed wallet sheet leaves no trace), so the hold's only release mechanism today is Stripe's own ~7-day authorization expiry; there is no "release immediately on leaving the screen" or "auto-release orphaned holds" logic, both still open per `BRI-588`'s unchecked acceptance criteria.

### 5. `PATCH /offers/:id/accept` (`:57-61`) — `acceptOffer`

The highest-risk single method in the module (`offers.service.ts:904-1192`). Full ordering, because ordering is explicitly load-bearing per the method's own doc comment:

1. `assertRespondable(offer, userId, 'accept')` — offer must be `pending`/`countered`, AND it must be `userId`'s turn (`nextResponderId`, derived from the last history entry's actor, not from `status` — this is the BRI-248 fix: `status` only encodes turn for round one).
2. Expiry re-check (`expiresAt < now`) — 400, even though the list-read path already sweeps expiry; this is the direct-call backstop.
3. **One-acceptance-per-listing application check** (`findUnpaidForListing`, excludes this offer id, filters to `status === 'accepted'`) — 409 if another unpaid offer on the same listing is already accepted. Source comment frames this as needed because `assertStillAvailable` "does not catch this" in the concurrent-accept race window — see the **Correction** callout under Prior-incident evidence above for why that's about timing within one race, not a claim that accept never commits inventory (it does, at step 12 below).
4. `assertStillAvailable(listingId, 'accept')` — reads live inventory availability (`onHand - committed - unavailable`, or falls back to `listing.stock` if no inventory row exists). 409 ("This item has already sold…") if exhausted. This is the BRI-270 backstop for a Buy Now sale (or another accepted-and-paid offer) that exhausted the listing between the buyer's last read and this accept.
5. Offer must carry a `paymentIntentId` — legacy pre-hold offers (none should exist going forward) get a 400 explaining there's no admin remedy.
6. **Capture the hold** (`stripe.captureOfferPaymentIntent`) — this is the irreversible-without-a-refund step, and it happens **before any database write**. A capture failure throws immediately (400) with no retry — **this is the confirmed-open `BRI-297` gap**: the client's resolved decision ("20a": retry 15 minutes, then clean-cancel with both parties notified and the listing fully reopened) is not implemented; today a declined card at accept time is a one-shot failure with no automatic retry window, and the offer is left exactly as it was (not advanced, not cancelled) — the seller has to tap Accept again later.
7. Every subsequent failure branch refunds the just-made capture (`refundCapturedOfferPaymentIntent`) rather than leaving a captured-with-nothing-to-show-for-it state: missing buyer address (extremely unlikely, address was required at offer time, but the buyer could have deleted their only one since), and order-creation failure (DB write throwing after a successful capture — refunds, logs at `error` level with an explicit "MANUAL INTERVENTION REQUIRED" marker if the refund itself also fails).
8. Order creation (`ordersRepo.createWithItems`) — happens **directly through the repository**, not through `OrdersService.create()` (see `offers.module.ts`'s comment: avoiding a third module-cycle on top of the existing Offers↔Payments forwardRef). This means **order-side guards in `OrdersService.create` (e.g. the mixed-seller-cart check, the `assertNoLeavingSeller` check beyond what offers already ran) do not apply to an offer-created order** — the two creation paths are genuinely parallel, not funneled through one service.
9. `confirmOrderPayment` — same call `OrdersService.confirmPayment` uses for Buy Now, so the Payment row and mark-sold logic is shared, not duplicated.
10. `repo.updateStatus(offerId, 'accepted', …)` — **this is the write the DB-level partial unique index actually guards.** Catches `P2002` → refund + cancel the just-created Order + notify the buyer + re-throw the same `ConflictException` the step-3 application check throws, so to the API consumer this looks identical whether the race was caught early or late.
11. `markOrdered([offerId], order.id)` — best-effort, logged on failure, never rolls back the accept (order is the source of truth).
12. `inventory.incrementCommitted` — real inventory commit (not the old `reserved` soft-label pre-BRI-233/BRI-79).
13. `cancelCompetingOffers([listingId], buyerId)` — closes every other **unpaid** offer on the listing **only if the sale exhausted it** (`available <= 0` after the commit above). Since every listing in this codebase is single-unit (confirmed via `BRI-589`'s "not applicable — listings have no quantity" resolution, citing `BRI-366`), this in practice closes every sibling, with Stripe hold release and a per-buyer notification (worded differently depending on whether the sibling's own offer was itself `accepted`-but-unpaid — "lost_after_accept" — or just an unanswered `pending`/`countered` — "sold_to_other" — or whether the *losing* buyer is actually the *winner* under a different offer, i.e. they bought their own open-offer item outright — "bought_yourself", BRI-270's own fix).
14. `closeSiblingOffers(listingId, offerId, title)` — an **unconditional catch-all**, re-queries `findUnpaidForListing` and closes anything still unpaid regardless of availability. **Confirmed gap, reading the code**: this path does **not** call `stripe.cancelOfferPaymentIntent` on the siblings it closes (no such call appears in `closeSiblingOffers`'s body, `:1206-1245`) — it only flips status and notifies. This is exactly what `BRI-589` reported ("closeSiblingOffers closes offers without cancelling their PaymentIntents") and Linear shows that ticket **Canceled**, not fixed, with the comment "Not applicable — listings have no quantity." In the current single-unit-only world this method is effectively unreachable dead code (step 13's `cancelCompetingOffers` already closes everything, hold-release included, before this runs) — but the gap is real at the code level and would resurface if multi-quantity listings are ever (re)introduced, since `closeSiblingOffers` is the one path with no hold-release call. Worth a regression test that fails loudly if `closeSiblingOffers` is ever reached with a non-empty `siblings` array.
15. Notifications to both parties — asymmetric copy depending on who acted (buyer-accepted-a-counter vs. seller-accepted-the-opening-offer), fixed by BRI-423 to stop the actor's own device getting the wrong-direction copy.

### 6. `PATCH /offers/:id/decline` (`:64-68`) — `declineOffer`

Turn-based (`assertRespondable`), same open/expiry checks as accept, **no availability check** (deliberately — "declining a dead offer commits the seller to nothing," per the `assertStillAvailable` doc comment and `BRI-270`'s explicit scoping). Releases the Stripe hold (`cancelOfferPaymentIntent`, best-effort, never throws) and notifies the other party. No inventory interaction (nothing was ever committed).

### 7. `PATCH /offers/:id/cancel` (`:71-75`) — `cancelOffer`

**Buyer-only**, and **not** turn-based — this is the one action deliberately exempt from `assertRespondable`'s turn check, because withdrawing isn't a move in the negotiation, it's leaving it (a buyer whose counter is sitting with the seller must still be able to pull out). `ForbiddenException` if the caller isn't `offer.buyerId`. Status must be `pending`/`countered` and unexpired. Releases the hold, notifies the seller. The mobile confirm-dialog copy ("releases the payment hold. No charge is made") is now **accurate** — at the time of `BRI-236`'s investigation this copy was aspirational (no hold existed at all pre-Epic-4); today `cancelOfferPaymentIntent` really is called.

### 8. `PATCH /offers/:id/counter` (`:78-86`) — `counterOffer`

Turn-based (either party — BRI-175 added buyer-counters-seller's-counter), same open/expiry checks. Additional checks unique to this verb:
- **Counter cap**: `countersBy(history, userId) >= MAX_COUNTERS_PER_PARTY` (3 per side) → 400, derived from `history` not a denormalized column (BRI-357).
- `assertStillAvailable` — same backstop as accept (BRI-270: don't let a seller counter on an item already sold through another channel).
- Ceiling: counter `<= listing.price` — applies to **either** party's counter.
- Floor: only when `userId === offer.buyerId` — the seller's own `minOfferPercent` binds the buyer, never the seller conceding against their own stated minimum.
- **Hold re-authorization**: a counter changes the amount, so the old hold (sized for the wrong total) must be replaced. Card path: authorize a fresh hold at the new total **first**, only cancel the old one once the new one is confirmed (so a Stripe hiccup mid-swap leaves the original hold intact, never a gap with no hold at all). **Wallet path is rejected outright** — "This offer's Apple Pay/Google Pay hold can't be re-authorized at a new amount" — there is no way to invoke the buyer's own wallet sheet remotely from either side, so a wallet-originated offer can only be declined and re-offered at the new price, never countered.
- Every counter **restarts the 24-hour window** (`OFFER_WINDOW_MS` from now) — BRI-357 resolved this against the originally-ambiguous "Business Rule 3" (`BRI-54` epic recorded it as a client-confirmation-pending open item; the resolution doc cited in-code is "the Buyer Oct 1 doc").

## Business-rule cross-reference to the canonical spec

`BRI-54` ("Epic — Offer Flow") is the authoritative business-rule document (12 numbered Business Rules, a 21-row scenario matrix, and its own 31-Aug-2026 acceptance-criteria retrospective against the actual codebase). Full detail and evidence classification in `offers.business-rules.json`; headline reconciliations worth calling out here because they changed the spec's own text, not just the code:

- **Business Rule 6** ("first confirmed payment wins… acceptance alone does not cancel the others") was explicitly **un-ticked by the epic's own 31-Aug-2026 retrospective** once `closeSiblingOffers`/`BRI-280` shipped the opposite behavior (cancel on acceptance, not on confirmed payment) — the epic's own text says *"This criterion and Business Rule 6 both need rewriting to match, or the code reverting."* Current code keeps the shipped (cancel-on-accept) behavior, which the signed-off `OfferAcceptConfirm.tsx` screen already promises the seller. Treat `BRI-54`'s original Business Rule 6 text as **superseded**, not current, for test-writing purposes.
- **Scenario 11** (seller accepts A, A never pays, B resumes) is **no longer reachable** — accept is now atomic (capture happens synchronously inside the same call that flips status), so there is no "accepted but unpaid" window for a reserve to lapse against. Do not write a test expecting this scenario; it was valid against the pre-Epic-4 design only.
- **Business Rule 11a / Scenario 20a vs 20b** (payment failure at capture) was resolved by the client toward 20a (15-min retry, then clean cancel) per a 31-Aug-2026 comment on the epic, tracked as its own ticket `BRI-297` — **still Backlog, not implemented**. Current code's actual behavior (immediate failure, no retry, offer left unchanged) matches **neither** 20a nor 20b fully. This is the single most consequential open gap in the module.

### Mobile (buyer + seller-via-same-app)

- `apps/mobile/src/services/offersApi.ts` — thin wrapper, one function per endpoint, all through `request<T>()` (no raw `fetch`). Confirms the mutual-exclusivity contract of `paymentMethodId`/`walletPaymentIntentId` in its own comment.
- `apps/mobile/src/utils/offerState.ts` — the single source for every "is this offer actionable" predicate (`OPEN_OFFER_STATUSES`, `isOfferOpen`, `isLapsed`, `canRespondToOffer`, `canCounterOffer`, `isAwaitingCounterparty`, `isSupersededByAcceptance`, `isAwaitingSellerAction`). Every one of these explicitly documents which server predicate it mirrors and which BRI ticket it was extracted from — this file is the designed fix for the whole "client predicate drift" bug class (BRI-172/202/235/248/252/280/784 all trace back to a screen re-deriving one of these instead of reading it here).
- `apps/mobile/src/store/offersStore.ts` — `loadOffers`/`add`/`setStatus`/`cancel`/`byId`. ### Web (seller + admin back-office)

- `apps/web/src/lib/sellerApi.ts` — **incoming-direction only** (`getOffers()` hardcodes `direction=incoming`), plus `acceptOffer`/`declineOffer`/`counterOffer`. **No web usage of `POST /offers`, `POST /offers/preview`, `POST /offers/wallet-hold-intent`, or `PATCH /offers/:id/cancel`** — confirmed by grep; the web portal is seller/admin back-office only, never a buyer surface, so creating/cancelling an offer (buyer-only actions) has no web entry point. `apps/web/src/app/seller/offers/page.tsx` is the consuming screen.

## Transaction-boundary / atomicity summary

- **Not one Prisma `$transaction`** spanning accept's full sequence — the method relies on (a) an external, effectively-irreversible Stripe capture happening first, (b) every DB write after it being either compensated with a refund on failure or being itself best-effort/non-critical (notifications, sibling-closing, back-link), and (c) a DB-level partial unique index as the final backstop against the one genuinely non-serializable step (two concurrent accepts on one listing). This is a deliberate design (external payment systems can't participate in a DB transaction), not an oversight — but it does mean a tester should look for **compensating-action correctness** (does the refund actually fire, is the order actually cancelled) rather than assuming `$transaction` makes the whole flow atomic.
- Inventory mutation (`incrementCommitted`) is a single call into `InventoryRepository`, which per `apps/api/CLAUDE.md`'s invariant runs inside its own `$transaction` together with the listing-status flip — this part **is** atomic, just not combined with the Stripe capture or the Order write into one larger transaction.
