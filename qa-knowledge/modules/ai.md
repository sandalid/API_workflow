# Module: AI

3 endpoints, `apps/api/src/ai/` (`ai.controller.ts`, `ai.service.ts`, `ai.repository.ts`, `ai-throttler.guard.ts`, `ai-error.ts`, `out-of-scope-terms.ts`, `shippability.ts`, `dto/`). The listing-creation AI-assist pipeline (OpenRouter → GPT-5-mini vision model), with an unusually extensive, well-documented prohibited-product/content-moderation layer. `ai.service.ts` is a very large file (700+ lines just to reach the class declaration) — read for controller/DTO/guard contract and the three public methods' bodies; the full prompt-construction and multi-flag disambiguation logic inside `runAnalysis`/`callModelAndParse` was not re-derived line-by-line (same scope-proportionality caveat as `feed.md`).

Analyzed against commit `91e0447b`. Evidence: extensive in-code BRI citations (`BRI-39`, `BRI-205`, `BRI-208`, `BRI-226`, `BRI-244`, `BRI-245`, `BRI-357`-adjacent, `BRI-489`/`BRI-491`/`BRI-488` for file-type validation, `BRI-582`, `BRI-799`), `docs/features/ai-analyze/` (5 files, not individually read this pass — flag for deeper follow-up if the prohibited-content logic needs its own dedicated review).

## Guard — class-level, applies to all three routes

`@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('SELLER')` at class level — **every AI endpoint requires an authenticated, confirmed seller**, not just any signed-in user. This is a real, source-confirmed restriction worth its own auth test: a signed-in buyer (not a seller) hitting any of these three routes should get a 403, not a 200.

## 1. `POST /ai/analyze` (`:25-32`)

- **Additional guard, method-level only**: `AiThrottlerGuard` — tracks by seller id (class-level guards run before method-level ones, so `req.user` is already populated when this guard evaluates). **Scoped to `analyze` only** — `regenerate` is deliberately excluded from this stricter throttle, per the controller's own comment, "since it's not called by the mobile app today" (see endpoint 3 below — confirmed true by a targeted grep, not just taken on faith).
- **Body**: `AnalyzeDto` — `images: string[]` (1-10 items, `MAX_ANALYZE_IMAGES = 10`, mirrors `MAX_LISTING_PHOTOS`; was 12 under an earlier ticket, BRI-39, now 10 per BRI-489's photo-cap reduction), `mode?: 'single' | 'bundle'` (default `'single'` — `'single'` rejects a photo set showing more than one product; `'bundle'` is the seller's explicit answer to a multi-item prompt, skipping that gate and asking the model to describe the group as one lot; a >5-item cap applies in **both** modes regardless), `parcel?: ParcelDto` (optional seller-corrected weight/dimensions that **replace** the model's own shippability estimate when the seller says the AI's guess was wrong — generously bounded, `@Max(10_000)` on each field, specifically to reject nonsense rather than to enforce the real shipping-carrier limits, which live entirely in `shippability.ts`'s own logic, not re-derived in this pass).
- **Implementation**: `analyze()` is a thin 1-line wrapper around `runAnalysis()` — identical code path to `regenerate()` below.

## 2. `GET /ai/price-comps` (`:34-41`)

- **No `AiThrottlerGuard`** — the controller's own comment explains why: "Read-only and cheap (one indexed query, no model call), so it sits under the global throttle rather than AiThrottlerGuard." Still gated by the class-level `JwtAuthGuard`+`RolesGuard('SELLER')`.
- **Query**: `PriceCompsQueryDto` — `categoryId`/`subcategoryId`/`typeId`, all optional strings (≤64 chars). **All three must be present for a real answer** — `getPriceComps()`'s own implementation returns an explicit "empty" result (`{ comps: [], range: null, count: 0, minComps, windowDays }`) immediately if any tier is missing, never a 400. The service's own doc comment states the reasoning precisely: *"'similar' means the same type, and a listing without a type has nothing to compare against, so it gets the not-enough answer, not a looser match."*
- **Business logic**: queries `AiRepository.findComparableSales` for sold listings matching all three tiers within `PRICE_COMPS_WINDOW_DAYS` (exact value not read in this pass — present in `ai.service.ts`'s constants, not independently confirmed). If fewer than `MIN_PRICE_COMPS` sales exist, returns the same "not enough" shape with the real `count` filled in (still not an error). Otherwise returns up to `PRICE_COMPS_SHOWN` sample comps (title + sold price) plus a `{ low, high, typical }` cents range (typical = median).
- **`BRI-799` design intent, confirmed by both the DTO's own comment and mobile's `getPriceComps` call site**: this is explicitly asked against the listing's **current, possibly seller-corrected** taxonomy tiers (as left on Manage Listing), not the AI's original first-pass classification — called from the "Set Your Price" step, not read directly off the initial analysis response.
- **Error handling**: a DB lookup failure is logged and re-thrown as `InternalServerErrorException` with a generic user-facing message — distinguishable from the "not enough comps" business case (which is always a 200 with `count` filled in), never conflated into the same response shape.

## 3. `POST /ai/regenerate` (`:43-49`)

- **Identical implementation to `analyze`** — same `AnalyzeDto` body, same `runAnalysis()` call (`regenerate()` is also a 1-line wrapper, confirmed by reading both method bodies in `ai.service.ts`). The only functional difference between the two endpoints today is which one carries `AiThrottlerGuard`.
- **Confirmed fully implemented end-to-end on both sides (backend route works, mobile has a typed `regenerateProduct()` wrapper with its own passing unit test asserting it POSTs to `/ai/regenerate`) but genuinely unreachable from any real screen** — targeted grep across `apps/mobile/src/**/*.tsx` (excluding tests) found zero call sites for `regenerateProduct`. This is not a contradiction between backend assumption and frontend reality (the backend comment "not called by the mobile app today" holds up under direct verification) — it is a fully-built, fully-tested, but currently-unused code path on both ends. Worth noting for test prioritization: `/ai/regenerate` can be tested for contract correctness, but there is no live user flow to reproduce via the app today — any manual/exploratory test against it would have to call the API directly, not navigate a screen to it.

## Server-side defense-in-depth worth documenting even though it's not its own endpoint

`AiService.checkProhibited(fields)` — a separate, non-route method applying the **same** prohibited-product word-boundary matching used during photo analysis, but against **typed text** instead. Called from "Fill in Manually" listing-creation paths that bypass AI analysis entirely (`BRI-226`) — i.e., a seller who gets rejected by the vision model (or opts out) and types their listing by hand is **still** checked against the prohibited-products list server-side before the listing can be created. This belongs conceptually to `listings`'s module (the actual call site is presumably in listing creation, not re-verified in this pass — cross-reference `modules/listings.md` during consolidation to confirm it's actually wired in). A DB lookup failure here throws `InternalServerErrorException` (fails closed, not open) — notably the **opposite** fail-direction from the Shippo/Intercom patterns documented elsewhere in this knowledge base, and worth its own explicit test: a prohibited-list-lookup outage should **block** listing creation, not silently let a prohibited item through.

## The prohibited-content disambiguation model (documented for completeness, not independently re-verified against the live prompt)

`ParsedAiResponseDto` carries five distinct boolean override flags the model can set to explain away an otherwise-false-positive keyword match against the seeded prohibited-products list: `prohibitedItemIsReplica` (toy/costume, not real), `isProhibitedWeapon` (the inverse — a genuine weapon even if the text doesn't match a seeded alias, e.g. an improvised one), `prohibitedTermIsGraphicOnly` (a printed design, not the product itself), `prohibitedThemeIsDecorative` (a costume/novelty/food item thematically referencing a weapon), `prohibitedMentionIsIncidental` (something in the photo's background, not the product being sold). Each is independently cited to its own BRI ticket in the DTO's code comments (`BRI-205`, `BRI-244`, `BRI-205` reopen, `BRI-582`) — strong evidence this is a genuinely iterated-on, previously-buggy classification surface, worth a dedicated deeper test pass of its own if prohibited-content false-positive/false-negative rates become a priority, beyond this knowledge base's current scope-proportional read.

## Frontend usage

### Mobile

- `apps/mobile/src/services/aiApi.ts` — `analyzeProduct`, `regenerateProduct` (see unreachable-but-built finding above), `getPriceComps`. Images are downscaled client-side (768px width, JPEG 0.6 compression) before being base64-encoded and sent — **every photo in the submission goes to the model, never truncated to "just the first few,"** per an explicit code comment: item-count detection is defined across the *entire* submission (`BRI-39`), so truncating client-side would let a multi-item submission spread over many photos misread as a single item and slip past the bundle cap. A 400 from either AI endpoint is treated as an **expected, handled outcome** (`expectedStatuses: [400]` on the `request()` call) with its own dedicated screen per rejection reason (multi-item, too-many-items, unshippable, prohibited, unclear photo) — not logged as a client error, specifically so a 500 (which does need attention) isn't buried among routine 400s.
- `AI_REQUEST_TIMEOUT_MS` (120s, per `overview.md`'s earlier architecture note) applies to both `/ai/analyze` and `/ai/regenerate` specifically — confirmed directly in `apiClient.ts`'s own comment.

### Web

No reference found in `apps/web/src/lib` or `apps/web/src/app` — confirmed by grep. Entirely a mobile seller-flow feature.

## Business-rule-relevant findings for consolidation

- **BR-AI-001**: all three endpoints require a confirmed seller role, not merely authentication — a signed-in non-seller account should 403.
- **BR-AI-002**: `/ai/price-comps` never 400s on missing tiers — it degrades to a "not enough data" 200. A test expecting a validation error for an incomplete query would be testing a behavior that doesn't exist.
- **BR-AI-003**: `/ai/regenerate` is throttled only by the global limiter, not `AiThrottlerGuard` — and currently has no live mobile UI entry point despite being fully implemented and tested on both ends.
- **BR-AI-004**: the typed-text prohibited-content check (`checkProhibited`) fails CLOSED on a DB error (blocks listing creation) — opposite fail-direction from several other external-dependency checks elsewhere in this codebase (Shippo, Intercom fail open). Flag this asymmetry explicitly in `gaps-and-conflicts.md` as a pattern worth a consistency discussion, not a defect in either direction individually.
