# Module: Feed

6 endpoints across two controllers — `feed.controller.ts` (`GET /feed`, `GET /feed/followed`) and `curation.controller.ts` (`admin/feed/curation` CRUD + `admin/feed/engagement-score/recompute`). Backed by a large, sophisticated service/repository (`feed.service.ts` 24KB, `feed.repository.ts` 42KB) implementing a multi-state personalization pipeline (`BRI-50`, status **QA Testing** in Linear). This module was **not read in full line-by-line depth** given its size relative to the 6-endpoint scope of this batch — the public-facing method signatures (`getPersonalisedFeed`, `getFollowedSellerListings`), the curation/engagement-score services (read in full, both small), the DTOs, and the constants file's tunable defaults were read directly; the ranking algorithm's full internal mechanics (query construction across `feed.repository.ts`'s 42KB) were not independently re-derived line-by-line and should be treated as **partially verified** — flag this explicitly in `endpoint-inventory.json` rather than claiming full depth.

Analyzed against commit `91e0447b`.

## 1. `GET /feed` (`feed.controller.ts:26-33`) — the personalised home feed

- **Auth**: `@UseGuards(JwtAuthGuard)` at class level — **authenticated only, as a deliberate product rule, not a technical limitation.** The controller's own doc comment is explicit: a guest has no home feed concept at all — the guest Home tab opens Category Browse/Search directly instead (per `BRI-71`/`BRI-147`, not independently re-verified, cited as source evidence from the comment). A guest reaching this endpoint is classified in-code as **a client bug**, and 401 is considered the *correct* answer, not a degraded-but-working fallback.
- **Query**: `GetFeedQueryDto` — `page` (optional, `@Min(1)`, default 1 applied in the controller not the DTO), `limit` (optional, `@Min(1) @Max(MAX_FEED_LIMIT=50)`, default 20 applied in the controller). Both `@Type(() => Number)`-transformed from query-string.
- **Three-state personalization pipeline** (`BRI-50`), resolved per-request via `resolveFeedState()`, not stored as a persistent user attribute:
  1. **Cold start** — no stated category preferences, no style signal, no behaviour signal. Blend target: curated (admin-picked) + algorithmically-scored, default **30% curated** (`DEFAULT_CURATED_PERCENT = 30`, env-overridable), rest score-ranked.
  2. **Preference-weighted** — once the viewer has `preferredCategoryIds`/`preferredStyles` signal.
  3. **Behaviour-weighted** — once `behaviourCategoryIds` (derived from actual view/like history via `category-affinity.service.ts`, not re-read in full this pass) is non-empty.
  - **One single assembly pipeline services all three states** — the code's own comment is emphatic that this is "not around assembly" (i.e., not three different code paths), only around *which signal is passed into* the same pipeline. This is a legitimate design choice worth preserving in any refactor and worth a test that asserts behavior continuity across state transitions (e.g. a user moving from cold-start to preference-weighted mid-session shouldn't see a structurally different response shape, just different ranking inputs).
  - **Last-resort name-derived audience lean**: if, and only if, the viewer is in cold-start state AND has stated/done nothing at all, a best-effort gender/audience guess derived from the account's display name (`name-gender.ts`, feature-flagged via `nameGenderEnabled`) is used as a tie-breaker signal. The code comment is explicit that this can **never** compete with or override a real stated/behavioural signal — it is discarded the instant any real signal exists. This is a sensitive mechanism (inferring a demographic attribute from a name) worth flagging for a privacy/fairness-oriented test reviewer even though it's scoped narrowly and overridden immediately by any real signal.
- **Hidden-seller exclusion (`BRI-470`)**: `excludeSellerIds` (from `UsersService.getHiddenSellerIds`) is resolved once per request and applied to **every** leg of the blend — curated, scored, and recent — so a seller the viewer has hidden can neither be surfaced nor counted toward pagination totals. The followed-shops rail (`/feed/followed`) explicitly needs no equivalent filter per the comment, because hiding a seller already un-follows them, and following an already-hidden seller is itself refused by `UsersService.followUser` (not independently re-verified in this module's own code — cross-reference the `users` module, already analyzed).
- **Response**: `FeedPage` — paginated listing data plus a `composition` field (`{ curated, scored, recent }` counts) that the mobile client treats as **diagnostic-only, never rendered to the user** (confirmed by the mobile `FeedPage` type's own doc comment). A `followed` field may also be present (recent listings from followed sellers, page-1-only preview of the full `/feed/followed` list) — **optional**, since an older API build may omit it; the mobile client treats an empty array and a missing field identically ("render nothing, no heading, no placeholder" — there is no empty state for this section at all).

## 2. `GET /feed/followed` (`:49-56`)

- **Auth**: same `JwtAuthGuard` class-level guard, same "no guest answer exists" reasoning (`BRI-287`).
- **Business logic**: the full, uncapped, paged version of the `followed` rail embedded (capped, page-1-only) inside endpoint 1's response — explicitly a sub-resource of the feed rather than its own concept, reusing the identical `GetFeedQueryDto` paging contract. Scoped to listings from sellers the viewer follows, posted within a recency window (`DEFAULT_FOLLOWED_RECENCY_DAYS = 14`, env-overridable via `followedRecencyDays`) — a listing from a followed seller older than 14 days will not appear here even though the seller is still followed.
- **Hydration parity**: uses the exact same `listings.hydrateRankedIds()` path as the main feed, so the response shape and the client's `ProductCard` renderer are identical across both endpoints — no second rendering path exists for this data.
- **Response**: `FollowedListingsPage` — `{ data, page, limit, total }`, no `composition` field (that concept doesn't apply to a single-source list).

## 3-6. Admin curation surface (`curation.controller.ts`) — all under `admin/feed`

- **Auth**: `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles(Role.ADMIN)` at **class level** — all four routes require the `ADMIN` role (checked against the JWT's `role` claim directly per `apps/api/CLAUDE.md`'s documented `RolesGuard` convention, not a live DB re-check the way `'SELLER'` role checks are).
- **Architectural note, explicit in-code**: this controller is deliberately routed under `admin/` as a **URL namespace only**, not owned by the `AdminModule` — curation reads/writes the feed domain's own `CuratedListing` table, and the author's comment states putting it in `AdminRepository` would mean two repositories owning the same table. Worth remembering when cross-referencing the `admin` module's batch: `admin/feed/*` routes are genuinely this module's territory, confirmed by the controller's own file location and ownership comment — not a gap or duplication to flag against the `admin` batch.
- **`GET admin/feed/curation`** — lists every curated listing (`CurationService.list()` → `repo.findCurationsForAdmin()`, not independently re-read for its exact select/order shape in this pass).
- **`POST admin/feed/curation`** — `CurateListingDto` (`listingId: string` 1-60 chars, `position?: number` ≥0 defaulting to 0 via `@Type(() => Number)`, `note?: string` ≤500 chars, "admin-only, never shown to buyers"). Implemented as an **upsert** (`repo.upsertCuration`) — re-curating an already-curated listing updates its position/note rather than erroring or duplicating, confirmed by the repository method name and the service's straightforward pass-through (no existence-check branch in `CurationService.curate`).
- **`DELETE admin/feed/curation/:listingId`** — removes a curation row; Prisma's `P2025` (record not found) is caught and re-thrown as a `NotFoundException` rather than a raw 500, with the comment explicitly noting "re-removing is not an error worth failing a request over" (i.e., the 404 is informational to the admin, not treated as a client-side bug class the way some other modules' "already in this state" errors are).
- **`POST admin/feed/engagement-score/recompute`** — manually triggers `EngagementScoreService.recomputeAll()` outside its normal nightly-cron schedule. **Full rebuild, not incremental** — explicitly documented as intentional: engagement scores decay continuously with time (exponential decay, `Math.pow(2, -ageDays/halfLifeDays)`, clamped to 1 for a future-dated bucket to guard against clock skew), so *every* row's score changes between runs even for untouched listings — an incremental update would still have to visit every row to apply decay, so a full rebuild "cannot drift" by design. **Explicitly safe to call repeatedly** (per the controller's own comment: "Safe to call repeatedly — the recompute is a full rebuild, not an increment"). Tunable via env (`FEED_ENGAGEMENT_WINDOW_DAYS` default unread in this pass but present in `feed.constants.ts`, `FEED_ENGAGEMENT_HALF_LIFE_DAYS`, `FEED_ENGAGEMENT_VIEW_WEIGHT`, `FEED_ENGAGEMENT_SAVE_WEIGHT`, `FEED_ENGAGEMENT_MAX_PER_USER_PER_DAY` — the last one caps how many views **one buyer** can contribute to **one listing's** score on **one day**, specifically so a listing's score "measures its popularity rather than one person's afternoon"; saves need no analogous cap since a `Like` is one row per buyer per listing by construction). Response: `RecomputeMetrics` — `{ scored, cleared, windowDays, durationMs }`, where `cleared` counts listings whose score row was deleted (not zeroed) because no signal remains inside the window — deliberately deleted rather than zeroed so the scores table stays proportional to currently-active listings instead of growing to one row per listing ever created.

## Frontend usage

### Mobile

- `apps/mobile/src/services/feedApi.ts` — thin wrappers for both public routes, both requiring an explicit `token` parameter (not using an implicit auth-header injection the way some other service files might) — a caller that forgets to pass a token gets a 401 from the server, not a client-side short-circuit.
- `Feed.tsx` (not read in full this pass, inferred from `feedApi.ts`'s own doc comments) falls back to "the plain listings endpoint" for guests — confirming the controller's "a guest reaching this endpoint is a client bug" framing is actually enforced client-side too (the guest-facing screen deliberately never calls this endpoint).

### Web

No reference found in `apps/web/src/lib` for either public feed route. **`admin/feed/curation` has no corresponding page found in `apps/web/src/app/admin`** either — confirmed by targeted search (`find ... -iname "*feed*" -o -iname "*curation*"` returned nothing, and `apps/web/src/lib/api.ts` has no `admin/feed`/`engagement-score` reference). This is a genuine, confirmed absence, not an unsearched gap: **the admin curation/recompute endpoints currently have no web UI at all** — they can only be exercised via direct API call (Swagger, curl, Postman), not through the product's own admin portal. Flag prominently in `gaps-and-conflicts.md`: either this is dead/aspirational tooling, or admin curation is performed out-of-band today and the web UI is a known missing piece.

## Business-rule-relevant findings for consolidation

- **BR-FEED-001**: the personalised feed is strictly authenticated-only by product decision (not a technical default) — a guest hitting `GET /feed` or `/feed/followed` gets 401, by design, not a degraded public response.
- **BR-FEED-002**: hidden-seller exclusion applies to every leg of the main feed blend; the followed-rail needs no separate exclusion because hiding already implies unfollowing (cross-reference `users` module's follow/hide logic to confirm, not re-verified independently here).
- **BR-FEED-003**: curation and engagement-score recompute are both safe/idempotent to call repeatedly (upsert-based curation, full-rebuild-based scoring) — relevant for a test scenario that wants to verify retry-safety without worrying about accumulating duplicate state.
- **Gap for consolidation**: admin curation/recompute has zero web UI — confirmed absence, worth its own `gaps-and-conflicts.md` entry.
- **Scope caveat for `endpoint-inventory.json`**: the ranking algorithm's full internal query construction (inside the 42KB `feed.repository.ts`) was not independently re-derived line by line in this pass — mark these 6 endpoints `analyzed` for contract/business-rule purposes (auth, DTOs, side effects, response shape are all source-confirmed) but note in the verification field that the deepest ranking-math internals are a shallower read than this knowledge base's norm elsewhere, should a future pass want to go deeper specifically into the scoring formula's exact row-level SQL shape.
