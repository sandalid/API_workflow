## Data-safety finding: `POST /seed/run` is additive-only, not destructive

Read in full (`seed.service.ts`, all 765 lines) and specifically grepped for `deleteMany`, `truncate`, `DROP TABLE`, `$executeRaw` — **zero matches**. Every one of its 7 internal seed steps (`seedBrands`, `seedSellers`, `seedAdmin`, `seedTaxonomyTree`, `seedListings`, `seedPromotions`, `seedProhibitedProducts`, `seedReviewers`, `seedProductReviews`) uses Prisma's `upsert` (21 upsert/findFirst/findUnique/create call sites total, confirmed by grep) keyed on a natural unique field (slug, email, code). The file's own doc comment on `seedTaxonomyTree` states the design intent explicitly: *"Upserts keyed on slug throughout, so re-seeding a database an admin has already edited adds what is missing without resetting their work — the same contract every other seeder here keeps."*

**Conclusion, source-verified**: calling this endpoint against a database that already has real data **cannot delete or overwrite existing rows it doesn't itself own by natural key** — it can only insert rows that don't yet exist (by slug/email/code) or no-op on ones that do (every `update: {}` in an upsert call is a genuine empty-object no-op, not a silent overwrite). It is safe to call repeatedly (idempotent) and safe to call against a database with pre-existing unrelated data, **subject to the caveats below**.

**Caveats, still source-verified, not hedged**:
- This only protects rows whose upsert key matches an *existing seed row*. If a real seller happens to register with the exact seed email (e.g. a fixture email under `@seed.redspur.com`), calling seed again would run that seeder's `update: {}` against the real user's row — a no-op in practice (the `update` clause is empty), so no data is overwritten, but it demonstrates the key collision is theoretically possible, just currently harmless because every upsert's `update` clause is empty.
- `seedListings` creates real `Listing` rows (with real inventory/category/brand FKs) — these are genuine, queryable listings after a seed run, not clearly marked as "test data" at the schema level (no `isSeed`/`isDemo` flag found). A database that has been seeded and later needs its demo listings removed has no corresponding "unseed" endpoint or flag to find them by — this is a real gap for environment cleanup, not a safety violation (nothing is corrupted), but worth flagging under dependency-map "cleanup limitations."
- Seeded users (admin, sellers, reviewers) get a bcrypt-hashed password hardcoded directly in `seed.service.ts` (admin's is overridable via `SEED_ADMIN_PASSWORD`, falling back to a hardcoded literal if unset). **Not reproduced here** per this task's "never include credentials...in the output" constraint — read `seed.service.ts` directly (`seedSellers`/`seedReviewers`/`seedAdmin`, roughly lines 355-495) if a test fixture needs to log in as a seeded user. This is a dev/test-fixture credential already committed in source, not a production secret, but still out of scope for this document.

## `POST /seed/run` (`seed.controller.ts:14-20`)

- **Auth**: **none** — no `JwtAuthGuard`, no `RolesGuard`, no API key check. The only gate is environment: `if (this.config.get<string>('NODE_ENV') === 'production') throw new NotFoundException()`. This means in **any** non-production `NODE_ENV` value (dev, staging, qa, test, undefined, a typo) the endpoint is callable by **anyone unauthenticated** who can reach the API host. The guard is environment-gated, not identity-gated — this is a real, source-verified distinction worth its own test case (confirm the 404 specifically in a `NODE_ENV=production`-configured instance, and confirm the *absence* of any auth requirement in every other environment).
- **Why 404, not 403**: the `@ApiOperation` summary states this is deliberate ("404s outside production... i.e. disabled in production") — a `NotFoundException` makes the route indistinguishable from one that doesn't exist at all in production, rather than confirming its existence with a 403. Standard "don't reveal the attack surface" practice, layered on top of (not a replacement for) the fact that the handler itself does nothing destructive.
- **Body**: none — no DTO, no input accepted.
- **Side effects**: see above — idempotent upserts across brands, 2 seller users + 1 admin user + N reviewer users, the full taxonomy tree (categories/subcategories/types/attributes), seed listings, 1 promotion code, prohibited-product entries, and product reviews (which read back the just-seeded listings/orders to attach to, per the in-code ordering comment: taxonomy before listings, reviews last).
- **Response**: `{ success: true, brands, categories, listings, users, prohibitedProducts, productReviews }` — all counts, confirming what was created/matched, not raw IDs. A caller cannot directly read back which specific IDs were (re)used from this response alone; it would need a follow-up read (e.g. `GET /brands`, `GET /categories`) to resolve concrete fixture IDs for a subsequent test call.
- **Synchronous**: `await`ed end-to-end, response only sent after every seed step completes — not queued/backgrounded. For a database with nothing seeded yet this runs all 9 steps' Prisma calls in sequence (several `Promise.all`'d internally per step, but steps themselves run sequentially per the in-code ordering comment) — no timing measurement was taken (no execution, per task constraints), but this is not a fire-and-forget job.

## Business-rule-relevant findings for consolidation

- **BR-SEED-001**: `POST /seed/run` is additive/idempotent by construction (upsert-only, zero destructive Prisma calls found) — safe to call repeatedly and safe against a database with pre-existing unrelated data. Evidence: direct source read, `seed.service.ts` in full.
- **BR-SEED-002**: the endpoint's only access control is `NODE_ENV !== 'production'` — no authentication of any kind otherwise. This is a real, intentional design choice (dev bootstrap tool), not a bug, but any test environment where `NODE_ENV` is not literally `'production'` has this endpoint open to any caller.
- A future testing agent **may** treat this as a legitimate, safe fixture-creation mechanism in a non-production test environment specifically because of finding BR-SEED-001 — but should still confirm the target environment's actual `NODE_ENV` value before relying on it, and should not assume it creates uniquely-identifiable-by-response-ID fixtures (it doesn't — see Response above).
