## Guards — mixed public/private per route (no class-level guard)

Per `apps/api/CLAUDE.md`'s documented pattern, `SellersController` is a "mixed public/private" controller — guards are applied per-route, not at the class. Verified route-by-route below; **7 of 26 routes have no auth guard at all** (public): `GET /sellers/:userId/shop`, `GET /sellers/check-shop-name`, `GET /sellers/confirm/:token`, and implicitly any route not listing `@UseGuards`. Every other route requires at minimum `JwtAuthGuard`; most of the account-management/dashboard routes additionally require `RolesGuard` + `@Roles('SELLER')` (live-checked `isSeller`, see `roles.guard.ts:42-48`, documented in `connect.md`).

## Endpoints

### 1. `GET /sellers/me/commission-rate`
- **File**: `sellers.controller.ts:66-72` → `PlatformSettingsService.getSettings()` (not `SellersService` — injected directly into the controller)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Business rule (BRI-602)**: returns the platform's CURRENT commission rate (`commissionRateBps`) — "the rate a NEW listing locks in at creation/relist time." Does **not** reflect any existing listing's own locked-in rate, which travels on the listing/offer/order rows themselves (`Order.commissionRateBps`, schema.prisma:808-813). A test must not assume this value equals what an existing order was actually charged.
- **Caching**: `PlatformSettingsService.getSettings()` is a read-through cache (`PLATFORM_SETTINGS_CACHE_KEY`, invalidated only by `PlatformSettingsService.updateSettings` — an admin-module action). A test that changes the commission rate via the admin endpoint and immediately re-reads this endpoint should see the new value (cache invalidated synchronously on write) — no manual cache-bust needed.
- **Response**: `{ commissionRateBps: number }` (basis points, e.g. `1000` = 10%, schema default).

### 2. `GET /sellers/:userId/shop`
- **File**: `sellers.controller.ts:75-78` → `SellersService.getPublicShopProfile` (`sellers.service.ts:313-320`)
- **Guards**: **none** — fully public, no auth header required.
- **Params**: `:userId` — any user id, not required to be a seller.
- **Business rule**: always returns 200 even for a non-seller/non-existent user — `shopName`/`shopLogo`/`shopTagline` are each nulled via `?? null` rather than a 404 (sellers.service.ts:315-319). A test should NOT expect a 404 for an invalid/non-seller `userId` here; it should expect `{ shopName: null, shopLogo: null, shopTagline: null }`.
- **Response**: `{ shopName: string|null, shopLogo: string|null, shopTagline: string|null }`

### 3. `GET /sellers/check-shop-name`
- **File**: `sellers.controller.ts:81-84` → `SellersService.checkShopName(name)` (`sellers.service.ts:324-341`)
- **Guards**: none — public.
- **Query**: `CheckShopNameQueryDto` — `name: string`, `@IsNotEmpty()` (BRI-503 fix: previously `@IsOptional()` with the controller defaulting to `''`, so a request with no `name` got a 200 `"too_short"` instead of the 400 every other missing-required-param gets everywhere else; now correctly 400s on a missing `name`).
- **Business rules**:
  - `name.trim().length < SHOP_NAME_MIN (3)` → `{ available: false, reason: 'too_short', suggestions: [] }`
  - `> SHOP_NAME_MAX (30)` → `{ available: false, reason: 'too_long', suggestions: [] }`
  - Taken (case-insensitive match against `SellerProfile.shopName`, `sellers.repository.ts:26-33`) → `{ available: false, reason: 'taken', suggestions: [...] }` — suggestions are generated by appending one of `['_shop','_co','_official','_us','1','2','3']` (in that order), truncated to fit `SHOP_NAME_MAX`, filtered against taken names, capped at 3 (`sellers.service.ts:344-358`).
  - Available → `{ available: true, suggestions: [] }`
  - **No `excludeUserId` support at this route** — `checkShopName`'s second parameter (`excludeUserId`) exists in the service signature but the controller never passes it (sellers.controller.ts:82-84 calls `this.sellers.checkShopName(query.name)` only), so a seller re-checking THEIR OWN current shop name would get `reason: 'taken'` against themselves. **This is a real gap worth a test**: `BRI-605` ("Check shop-name availability when a seller renames their shop," open/Backlog per Linear) is exactly this scenario — renaming to a name close to one's own, or re-submitting the unchanged current name, may incorrectly report "taken." `SellersService.apply()` DOES pass `userId` as `excludeUserId` when checking at account-creation time (`sellers.service.ts:380`), but this standalone GET endpoint — used for the live typing-check UX — does not.
- **Response**: `{ available: boolean, reason?: 'too_short'|'too_long'|'taken', suggestions: string[] }`

### 4. `POST /sellers/phone-otp/request`
- **File**: `sellers.controller.ts:87-93` → `SellersService.requestPhoneOtp` (`sellers.service.ts:239-250`)
- **Guards**: JwtAuthGuard only (no RolesGuard — a non-seller can call this; it's the mechanism to BECOME a confirmed seller).
- **Rate limit**: `@Throttle(STRICT)` = 10 requests/60s (sellers.controller.ts:16,47,89) — same rationale as auth OTP endpoints: brute-force/enumeration target plus real per-SMS Twilio cost.
- **Body**: `RequestPhoneOtpDto` — `phoneNumber: string`, `@Matches(/^\d{10}$/)` — US-only, raw 10-digit national number, no `+1`/punctuation (client must strip formatting before sending).
- **Business rules**:
  - Formats to E.164 (`+1${phoneNumber}`) server-side before calling Twilio (`toE164`, sellers.service.ts:223-225).
  - **QA test-number bypass**: `+12264550694` (hardcoded, `PHONE_OTP_TEST_NUMBERS`, sellers.service.ts:62) gets Twilio's fixed code `'000000'` instead of a random SMS code — gated additionally on `!isProduction()` (`NODE_ENV !== 'production'`, sellers.service.ts:227-229,241). **This is the sanctioned test fixture for automating the full phone-OTP round trip without receiving a real SMS** — use this number in any non-production test environment; it will NOT work in production and must not be assumed to.
  - No app-level cooldown/expiry tracking — Twilio Verify owns code generation, expiry (~10 min default), and resend throttling server-side.
- **Response**: `{ status: string }` (Twilio Verify's own status string, e.g. `'pending'`).
- **Errors**: mapped via `mapTwilioError` (sellers.service.ts:285-311) to structured `PhoneOtpErrorCode`s: Twilio code `60203` or HTTP `429` → `429 PHONE_OTP_RATE_LIMITED`; anything else unmapped → `503 ServiceUnavailableException` ("Couldn't send or verify your code right now") — this service **halts rather than silently falling back** on a genuine Twilio failure (documented pattern, same posture as the Shippo integration).

### 5. `POST /sellers/phone-otp/verify`
- **File**: `sellers.controller.ts:96-102` → `SellersService.verifyPhoneOtp(userId, dto)` (`sellers.service.ts:259-272`)
- **Guards**: JwtAuthGuard only
- **Rate limit**: `@Throttle(STRICT)` (10/60s)
- **Body**: `VerifyPhoneOtpDto` — `phoneNumber` (same 10-digit pattern), `code: string` `@Matches(/^\d{6}$/)`.
- **Business rules**:
  - A wrong code is a normal Twilio response (`valid: false`) → `400 { code: 'PHONE_OTP_INVALID', message: "That code isn't right." }` — NOT a thrown Twilio SDK error.
  - An expired/already-checked verification or exhausted attempt count IS a thrown Twilio error: code `20404` → `400 PHONE_OTP_EXPIRED`; code `60202` → `429 PHONE_OTP_LOCKED` ("Too many tries…").
  - On success, writes `User.phoneVerifiedNumber = <E.164>`, `User.phoneVerifiedAt = now()` (`sellers.repository.ts:96-101`) — this is the marker BOTH `apply()` (30-min TTL) and `ConnectService.createPayoutAccountSession` (5-min TTL, different gate entirely) read back later. **Same underlying field, two different TTLs for two different purposes** — a test asserting the TTL must target the right call site.
- **Response**: `{ verified: true }`

### 6. `POST /sellers/apply`
- **File**: `sellers.controller.ts:105-110` → `SellersService.apply(userId, email, name, dto)` (`sellers.service.ts:360-429`)
- **Guards**: JwtAuthGuard only
- **Body**: `ApplySellerDto` (`dto/apply-seller.dto.ts`) — full field list:
  - `sellerType: 'individual'|'business'` — **required** (BRI-504: previously optional, meaning a direct API call could activate a seller with no Tax ID on file; now required both client- and server-side).
  - `legalName?: string` (max 120) — optional, nullable column.
  - `taxId: string` — **required**, format depends on `sellerType` via a custom cross-field validator (`IsTaxIdForSellerType`, apply-seller.dto.ts:70-90): `individual` → SSN pattern `^(\d{9}|\d{3}-\d{2}-\d{4})$`; `business` → EIN pattern `^(\d{9}|\d{2}-\d{7})$`. **SECURITY**: this raw value is never persisted, logged, or returned by any endpoint — `deriveTaxIdLast4` (sellers.service.ts:93-96) reduces it to the last 4 digits at the service boundary; anything that doesn't yield ≥4 digits stores `undefined`, never a padded/partial string.
  - `shopName: string`, length `[SHOP_NAME_MIN, SHOP_NAME_MAX]` = `[3, 30]`.
  - `shopTagline?`, `shopLogo?` — free strings, optional.
  - `phoneNumber: string` — required, no format validation at THIS DTO layer (the phone-OTP DTOs validate the 10-digit shape; this field is checked for E.164 equality against the OTP-verified number inside the service, not by `class-validator`).
  - `sellerCategories?: string[]` — optional (the redesigned onboarding dropped the category-picker step).
  - `address: SellerAddressDto` — **required as an object** (`@IsDefined` + `@IsObject`, BRI-505 fix: `@ValidateNested` alone silently skips validation of an ABSENT property, so a body with no `address` at all used to 500 instead of 400). Fields: `addressLine1`, `city` (both `@IsNotEmpty`), `state` (`@IsIn(US_STATE_CODES)`, uppercased via `@Transform`), `zip` (`@Matches(US_ZIP_PATTERN)` — 5-digit or ZIP+4), `country?` (defaults to `'US'` in the service, not the DTO). The whole DTO is `@IsConsistentUsAddress()`-decorated (class-level) — rejects an internally inconsistent city/state/zip combination (e.g. a real ZIP paired with the wrong state) BEFORE Shippo is ever called.
- **Business rules (in order, every check before any write)**:
  1. 404 if user not found.
  2. `409 Conflict` "You are already a verified seller" if `user.isSeller` is already true — this endpoint is NOT idempotent/re-appliable once active.
  3. **Phone-verification trust boundary** (sellers.service.ts:365-378): requires `user.phoneVerifiedNumber === E164(dto.phoneNumber)` AND `phoneVerifiedAt` within `PHONE_VERIFICATION_TTL_MS` = **30 minutes** of now. An exact E.164 match is required — editing the phone number after verifying invalidates the trust, and a stale (>30 min) verification from an abandoned-then-resumed session also fails. Failure → `400` "Please verify your mobile number before continuing." The mobile client's own `phoneVerified` flag on `SellerOnboardingContext` is UX-only state; this server check is the real boundary.
  4. Shop-name uniqueness re-check at submit time (`409` "That shop name is already taken…") — same check as endpoint 3 but THIS ONE correctly passes `userId` as `excludeUserId` (sellers.service.ts:380).
  5. **Ship-from address deliverability** (BRI-507, sellers.service.ts:383-395): calls Shippo's `validateAddress` on the submitted address BEFORE any write. Blocks with a `400` (Shippo's own message) on an explicit "not deliverable" answer. **Fails OPEN** on a Shippo API error/timeout — logs a warning and lets the address through unvalidated (`assertShipFromDeliverable`, sellers.service.ts:565-582) — onboarding must not depend on Shippo being up. A test should be able to distinguish "Shippo said undeliverable" (hard 400) from "Shippo was down" (silently passes).
  6. Upserts `SellerProfile` (not a plain create — handles a re-apply-after-prior-partial-state edge case via `prisma.sellerProfile.upsert`).
  7. **Instant activation**: `this.repo.activate(userId)` sets `isSeller: true` immediately, same request — "the redesigned mobile onboarding activates the seller account immediately (no email-confirmation step)." No Stripe Connect requirement to activate — `isSeller` and Stripe verification are independent gates (a seller can be `isSeller: true` with zero payout capability).
  8. Sends a welcome email (`MailService.sendSellerWelcome`) — **best-effort**: a mail failure is logged, not thrown; the HTTP response still succeeds.
  9. **NOT enforced anywhere in this path**: an age/date-of-birth gate on the SSN/EIN step. `REDB1-146`/`BRI-810` (Linear, status `Todo`) tracks this as a known compliance gap — PRD §6.1 requires an under-18 block on financial agreements and it does not exist in `ApplySellerDto`/`SellersService.apply` today (confirmed by reading both).
- **Response**: `{ message: 'Your seller account is live', isSeller: true }` — note this is a DIFFERENT shape from `resendConfirmation`'s `{ message: string }` (no `isSeller` there) and from `confirm`'s `{ success: true }` — three different legacy/current response shapes for three related endpoints; a test asserting response shape must target the exact endpoint, not assume parity.
- **Errors**: `404`, `409` (already seller / shop name taken), `400` (phone not verified / address undeliverable / DTO validation).

### 7. `POST /sellers/resend-confirmation`
- **File**: `sellers.controller.ts:113-118` → `SellersService.resendConfirmation` (`sellers.service.ts:431-462`)
- **Guards**: JwtAuthGuard only
- **Business rules — this endpoint now serves TWO different legacy/current purposes depending on account state**:
  - If `user.isSeller` is already true (the normal case under instant activation): just RE-SENDS the welcome email, best-effort. Does not touch tokens.
  - If NOT a seller but has a `sellerProfile` (a legacy pending application from before instant activation): mints a NEW `sellerConfirmToken` (random 32 bytes hex) + 24h expiry, sends a confirmation email with a `${WEB_URL}/seller/confirm?token=...` link.
  - If NOT a seller AND no `sellerProfile` at all: `400 BadRequestException` "No seller application found. Please apply first."
- **Response**: `{ message: string }` (either `'Welcome email resent'` or `'Confirmation email resent'`).
- **Note**: given instant activation is now the live onboarding path, the token-minting branch is effectively legacy/dead-code-in-practice for new sellers — but still reachable and testable for an account seeded directly with a `sellerProfile` + `isSeller: false` (a state a test fixture CAN construct even though the live `apply()` flow no longer produces it).

### 8. `GET /sellers/confirm/:token`
- **File**: `sellers.controller.ts:121-125` → `SellersService.confirm(token)` (`sellers.service.ts:464-480`)
- **Guards**: none — public (clicked from an emailed link, no session).
- **Business rules**: `400` "Invalid or expired confirmation link" if no user matches the token OR `sellerConfirmExpiry` is null; `400` "Confirmation link has expired…" if expiry is in the past. On success: `activate(userId)` (same as `apply`'s step 7 — sets `isSeller: true`, clears the token/expiry) + best-effort welcome email.
- **Response**: `{ success: true }` (controller wraps the void service call, sellers.controller.ts:122-124) — no account/profile data returned.
- **Dependency note**: this is the legacy-path counterpart to `resendConfirmation`'s token-minting branch — only reachable for a seeded pending-application fixture, not the live instant-activation flow.

### 9. `GET /sellers/me`
- **File**: `sellers.controller.ts:128-133` → `SellersService.getProfile(userId)` (`sellers.service.ts:495-524`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Business rules**: `404` "Seller profile not found" if `!user.sellerProfile` (reachable even for an `isSeller: true` account only via a direct DB inconsistency — in practice every active seller has a profile, since `apply()` upserts one before activating). Every onboarding-step-1 field (`sellerType`/`legalName`/`taxIdLast4`) is nullable and rendered `null` (not omitted) for any seller who onboarded before BRI-285 — "the UI renders those rows as absent." `payout` is a bank-account SUMMARY ONLY — full account/routing numbers are read from `SellerBankAccount` server-side but never serialized into the response (`accountLast4` helper strips to last 4, sellers.service.ts:100-103); no endpoint in this module exposes the full bank details.
- **Response fields**: `shopName, shopTagline, shopLogo, phoneNumber, sellerCategories, addressLine1, city, state, zip, country, sellerType, legalName, taxIdLast4, notifyFollowersOnNewListing, payout: { accountHolderName, bankName, accountNumberLast4 } | null, isSeller`.

### 10. `PATCH /sellers/profile`
- **File**: `sellers.controller.ts:136-142` → `SellersService.updateProfile` (`sellers.service.ts:536-556`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Body**: `UpdateSellerProfileDto` — every field `@IsOptional()`, but each present field is ALSO `@IsNotEmpty()` where the underlying column is `NOT NULL` (`shopName, phoneNumber, addressLine1, city, state, zip`) — a caller may OMIT a field, but sending `{ city: '' }` is rejected (400), since the column can't be blanked and the seller "can only re-enter [it] by contacting support" per the code comment. `shopName` re-validated to `[3,30]` length; `state`/`zip` same `IsConsistentUsAddress`/US-state/ZIP rules as `apply`. `notifyFollowersOnNewListing?: boolean` (BRI-371). `country` is deliberately NOT an updatable field (US-only product, column defaults `'US'`, nothing lets a seller change it).
- **Business rule**: if ANY of `addressLine1`/`city`/`state`/`zip` is present in the body, re-runs the Shippo deliverability check (`assertShipFromDeliverable`) against the FULL resulting address (existing values merged with the partial update) — same fail-open-on-Shippo-error, hard-400-on-explicit-undeliverable behavior as `apply`.
- **Response**: the SAME shape as `getProfile` — "both callers treat the response as a whole profile and swap their cached copy for it" (sellers.service.ts:529-534 doc comment) — a regression here (e.g. returning the raw Prisma row instead of calling `getProfile` again) silently drops the `payout`/`isSeller` fields client-side until the next full reload. Worth a dedicated test asserting the PATCH response round-trips `payout` and `isSeller` even when neither was in the request body.

### 11. `GET /sellers/me/orders/stats`
- **File**: `sellers.controller.ts:145-150` → `SellersService.getOrderStats` (`sellers.service.ts:584-596`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Query**: `GetOrderStatsQueryDto` — `from?`, `to?` (both plain `@IsString()`, NOT `@IsDateString()` — no format validation at the DTO layer; an arbitrary string reaches `new Date(from)` in the service and silently becomes `Invalid Date` rather than a 400).
- **Business rules**: `byStatus` (counts per `OrderStatus`, all 8 enum values always present, zero-filled), `byPayment` (`paid|pending|failed`, derived from `Payment.status`, NOT from `Order.status` directly except that `cancelled` always counts as `failed`), `cancellationRate` — see dedicated note below (BRI-143: this follows the SAME `from`/`to` window as the rest of the dashboard now; previously hardcoded to a rolling 90 days regardless of the selected range, which is why the card read "last 90 days" under a "Last 7 days" dropdown).
- **`cancellationRate` sub-object** (`sellers.repository.ts:172-195`): `{ ratePct, sellerCancelledCount, totalCount, windowDays }`. Only counts cancellations attributable to the SELLER (`isSellerDirectCancellation` — `common/utils/cancellation.util.ts:62-65` — matches the `OrderStatusHistory.description` PREFIX string, `'Cancelled by seller'` or `'Auto-cancelled — seller did not ship within the window'`). A BUYER-requested cancellation NEVER counts toward this rate, even once the seller approves it — "that's the buyer's call, not a seller reliability signal." `windowDays` is returned (not assumed client-side) and counted INCLUSIVELY (`from = today - 6 days` means "last 7 days", today included). Default window with no `from`/`to`: rolling 90 days (`since = until - 89 days`).
- **Response**: `{ byStatus: Record<OrderStatus, number>, byPayment: { paid, pending, failed }, total, cancellationRate: {...} }`

### 12. `GET /sellers/me/orders`
- **File**: `sellers.controller.ts:153-164` → `SellersService.getOrders` (`sellers.service.ts:662-711`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Query**: `GetSellerOrdersQueryDto` — `page=1`, `limit=20` (max 100, both `@Type(() => Number)` + `@IsInt @Min(1)`), `status?: string` (free string, not `@IsEnum` — an invalid status silently matches zero rows rather than 400ing), `paymentStatus?: 'paid'|'failed'|'pending'` (also a free string at the DTO layer; the repository's `paymentWhere` switch only recognizes those three literals — anything else falls through to `{}`, i.e. no filter applied, which could surprise a test expecting a 400 on a typo).
- **Business rule — `paymentStatus` derivation** (`sellers.repository.ts:205-214`, matches the per-order derivation in `getOrderById`/`getOrders` mapping): `paid` = `Payment.status === 'succeeded'`; `failed` = `Payment.status IN (failed, canceled)` OR `Order.status === 'cancelled'`; `pending` = everything else (explicitly NOT cancelled AND NOT succeeded/failed/canceled). **This is a derived field, not a stored column** — a test must not try to filter/assert by writing `Payment.status` alone without considering `Order.status === 'cancelled'`'s override into `failed`.
- **Pagination**: page/offset (`getPaginationParams`), NOT cursor-based — consistent with `overview.md`'s "page/offset for stable admin/seller lists."
- **Response**: `{ data: SellerOrder[], total, page, limit }` — each row's shape mirrors `getOrderById`'s list-shape subset (see endpoint 15) minus `taxCents`/`discountCents`/`cardBrand`/`cardLast4`/`shippingAddress`/`cancelRequestedBy` (those are detail-only fields).

### 13. `GET /sellers/me/orders/chart`
- **File**: `sellers.controller.ts:167-177` → `SellersService.getOrderChart` (`sellers.service.ts:1287-1292`, bucket-building logic in `buildChartBuckets`, sellers.service.ts:120-202)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Query**: `GetOrderChartQueryDto` — `from?`, `to?` (plain strings, converted with `new Date()` in the controller — sellers.controller.ts:173-174), `groupBy: 'day'|'week'|'month'` defaults `'day'` (`@IsIn`, validated).
- **Business rules**:
  - Excludes `cancelled` orders entirely from the chart data (`findOrdersForChart`, sellers.repository.ts:444-454 — `status: { not: 'cancelled' }`).
  - **`day` bucketing uses LOCAL server time zone**, not UTC (`dayKey` helper, sellers.service.ts:111-118, explicit comment: "Using `toISOString().slice(0,10)` for one side and local methods for the other side silently desynced 'Today' by a day for any server running in a non-UTC time zone" — this was a real prior bug class, now guarded by using local-TZ methods consistently on both the per-order bucket key and the cursor walk). **A test asserting exact day-bucket boundaries must account for the API server's configured time zone**, not assume UTC.
  - Last label is overwritten to a human string: `'Today'` for `day`, `'Now'` for `week`/`month` groupings (regardless of the actual date in that bucket).
  - With no `from`, defaults to the earliest order's `createdAt` (or `now()` if there are no orders at all); with no `to`, defaults to `now()`.
- **Response**: `{ labels: string[], orders: number[], revenue: number[] }` — three parallel arrays, one entry per bucket.

### 14. `GET /sellers/me/orders/:id`
- **File**: `sellers.controller.ts:180-188` → `SellersService.getOrderById` (`sellers.service.ts:598-660`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Business rules**: ownership-scoped lookup (`findOrderByIdForSeller(orderId, sellerId)` — a seller can never read another seller's order by id, not even a 403, it's a flat `404` "Order not found"). **Side effect on read**: `ordersService.maybeAutoApproveCancellation(o)` runs on every GET (sellers.service.ts:601) — if a pending buyer cancellation request has exceeded its 24h auto-approve window, THIS READ can mutate the order's status as a side effect before returning it (re-fetches after, sellers.service.ts:602-604). **A GET endpoint here is not side-effect-free** — same pattern as `connect.md`'s `getStatus`.
- **Response fields** (detail shape): `id, status, paymentStatus (derived, see #12), subtotalCents, shippingCents, taxCents, discountCents, totalCents, platformFeeAmountCents, sellerAmountCents (BRI-602 — this order's own LOCKED-IN commission split, never the current platform rate), trackingNumber, trackingUrl, estimatedDeliveryDate, estimatedDeliveryTime, createdAt, cancelRequestedAt, cancelRequestReason, cancelRequestedBy, disputeStatus (internal Dispute model), stripeDisputeStatus (real Stripe chargeback — see connect.md's StripeDispute — DISTINCT field, can both be non-null independently), cardBrand, cardLast4 (BRI-816, snapshotted at order-creation, survives the buyer later removing that card), shippingAddress: {...}, buyer: {...}, items: [...]`.

### 15. `PATCH /sellers/me/orders/:id/ship`
- **File**: `sellers.controller.ts:191-201` → `SellersService.shipOrder` (`sellers.service.ts:713-757`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Body**: `ShipOrderDto` — `trackingNumber?`, `trackingUrl?`, `estimatedDeliveryDate?` (`@IsDateString`), `estimatedDeliveryTime?` — **all optional**, because a real Shippo-purchased label can supply tracking automatically (see below).
- **Business rules — this is the most externally-dependent write in the module**:
  1. `400` if order is already `delivered`/`cancelled`.
  2. **Never re-purchases a label the seller already bought via the Buy-Shipping-Label flow** (endpoints 16/17 below) — checks for an existing `purchased` `Shipment` row (kind `'outbound'`) FIRST; if found, reuses its tracking data rather than running the auto-purchase path. This guards against silently overwriting a seller's deliberately-chosen carrier/rate with the cheapest-rate auto-purchase (confirmed root cause of a real carrier-choice production bug, 2026-09-14).
  3. If no existing purchased label: attempts a LIVE Shippo auto-purchase (`purchaseOutboundLabel`, cheapest rate, derived from the LISTING's package dimensions, not seller-typed at ship time) — but only if every item has complete package dimensions, a resolvable buyer ship-to address (from the order's checkout-time snapshot) and seller ship-from address (from `SellerProfile`) exist, and the parcel is within the 50lb/108in cap (`MAX_PARCEL_WEIGHT_OZ`/`MAX_PARCEL_LENGTH_PLUS_GIRTH_IN`, `shipping.constants.ts:8-10`). Any of those missing → silently falls back to the client-supplied `dto.trackingNumber`/`dto.trackingUrl` (the historical/mock behavior) — **not an error**.
  4. A GENUINE Shippo failure (API error, or a response that isn't a usable purchased label) during the auto-purchase attempt is NOT a silent fallback — it throws `503 ServiceUnavailableException` with the shared `SHIPPO_UNAVAILABLE_MESSAGE` ("We cannot proceed. Please contact Redspur administration.") and notifies every admin (`notifyAdminsShippoFailure`, in-app). This distinction (missing-preconditions → silent client-data fallback; genuine-API-failure → hard halt + admin alert) is load-bearing and easy to get backwards in a test — write separate scenarios for each.
  5. **Concurrency guard**: `ShipmentsRepository.claimForPurchase` is an atomic claim taken before the Shippo round-trip — a double-tap/retry racing the label purchase either finds `'already_purchased'` (returns the existing label, no second Stripe/Shippo charge) or `'in_progress'` (`409 Conflict` "already being purchased — try again shortly"). Released on any failure path so a genuine retry after an outage isn't permanently stuck.
  6. First successful ship stamps `Order.shippedAt` ONLY ONCE (`updateMany({ where: { shippedAt: null } })`, sellers.repository.ts:293) — re-sending tracking on an already-shipped order does not push the ship-time stamp later (BRI-336).
  7. **This endpoint BYPASSES `OrdersService.updateStatus`'s own state machine** (it writes `status: 'shipped'` directly via its own repository call) — so it must independently fire the buyer "Order Shipped" notification itself (BRI-400: previously it didn't, silently). A test covering buyer notifications on ship must hit THIS endpoint, not assume `PATCH .../orders/:id/status` is the only path that notifies.
- **Response**: `{ id, status, trackingNumber }`

### 16. `POST /sellers/me/orders/:id/shipping-rates`
- **File**: `sellers.controller.ts:204-214` → `SellersService.getShippingRates` (`sellers.service.ts:994-1058`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Body**: `GetShippingRatesDto` — `weightLb, lengthIn, widthIn, heightIn`, all `@IsNumber() @Min(0.01)` — this is SELLER-TYPED at ship time (Buy Shipping Label flow), unlike `shipOrder`'s auto-purchase which reads dimensions off the LISTING. Two independent sources of parcel dimensions in this module.
- **Business rules**: pre-checks shippability via `checkShippability(dto)` (shared with the AI listing-estimate gate, `ai/shippability.ts`) — `400` with Shippo's cap-exceeded reason if over. `400` if the order's shipping address snapshot is incomplete, or if the seller has no profile/address on file ("Add your shop address in Seller Settings before buying a label"). On a genuine Shippo failure: THROWS (does not fall back) — "unlike the other Shippo call sites, this endpoint IS the real-time UI the seller is looking at." **Side effect**: upserts a `Shipment` row (`kind: 'outbound', status: 'created'`) recording which Shippo shipment these rates were quoted against — this is what `purchaseShippingLabel` (endpoint 17) later checks a `rateId` against, to refuse a cross-order rate reuse.
- **Response**: `ShippingRate[]` — `{ rateId, carrier, service, amountCents, estimatedDays, cheapest: boolean }[]`, sorted cheapest-first, `cheapest: true` only on index 0.

### 17. `POST /sellers/me/orders/:id/shipping-label`
- **File**: `sellers.controller.ts:217-227` → `SellersService.purchaseShippingLabel` (`sellers.service.ts:1069-1202`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Body**: `PurchaseShippingLabelDto` — `rateId: string` (must be a rate previously returned by endpoint 16).
- **Business rules**:
  1. `400` if no shipping-rates quote exists yet for this order ("Request a shipping rate for this order before purchasing a label").
  2. **Idempotency against client retry-after-success**: if the quoted `Shipment` is already `purchased` with a tracking number, returns the EXISTING label rather than calling Shippo again — "a network timeout between us and the client... would call purchaseLabel a second time and buy a second, real, paid label" otherwise.
  3. Same atomic `claimForPurchase` concurrency guard as `shipOrder` (`'already_purchased'` → return existing; `'in_progress'` → `409`).
  4. **Cross-order rate-ownership check**: `rate.shipmentId !== quotedShipment.shippoShipmentId` → `400` "This rate was not quoted for this order" — Shippo's `rateId` is a global opaque token, not order-scoped on Shippo's side; without this check a seller with multiple open orders could quote for order A and purchase that `rateId` against order B, producing a real label addressed to A's buyer while B's own records (and the buyer B sees) claim it shipped correctly. **High-value security/correctness test**: attempt to purchase order B's label using a `rateId` quoted for order A, expect `400`.
  5. A genuine Shippo failure (rate lookup, or purchase itself) → `503` with `SHIPPO_UNAVAILABLE_MESSAGE`, admin-notified. A specific Shippo `circuit_breaker_error` code (confirmed observed live, 2026-09-11, USPS outage) is logged distinctly internally but surfaces the SAME user-facing halt message — a test should not expect different client-visible copy for a carrier outage vs. any other Shippo failure.
- **Response**: `{ trackingNumber, trackingUrl, labelUrl, qrCodeUrl }` — does NOT itself mark the order shipped; the mobile `ShipLabelQr.tsx`'s "I've shipped it" button still calls `PATCH .../ship` (endpoint 15) afterward with this real tracking data.

### 18. `PATCH /sellers/me/orders/:id/status`
- **File**: `sellers.controller.ts:230-240` → delegates straight to `OrdersService.updateStatus(sellerId, orderId, dto)` (owned by the `orders` module — `apps/api/src/orders/orders.service.ts:1336-1380`)
- **Guards**: JwtAuthGuard + RolesGuard(`'SELLER'`)
- **Body**: `UpdateOrderStatusDto` (orders module) — `status` (`@IsEnum(OrderStatus)`), `description?`, `trackingNumber?`, `trackingUrl?` (`@IsUrl`, unlike `ShipOrderDto`'s plain string — inconsistent validation strictness for conceptually the same field across the two endpoints, worth flagging), `estimatedDeliveryDate?`, `estimatedDeliveryTime?`.
- **Business rules (owned by `orders` module, documented here since this is this route's only entry point)**:
  - Ownership check: `403 Forbidden` "Access denied" if `order.sellerId !== sellerId` (note: DIFFERENT error code from `getOrderById`'s flat `404` for the same kind of ownership mismatch — a cross-seller probe gets `403` here but `404` there. **Flag for the coordinator**: this inconsistency between the `sellers` controller's own routes is a real, user-visible information-disclosure difference (403 confirms the order exists; 404 doesn't) that a security-minded test should document even though it spans two different service methods.)
  - `SELLER_ALLOWED_STATUSES = ['processing','packed','shipped','out_for_delivery','delivered','returned']` (orders.service.ts:45) — a seller may never set `placed` or `cancelled` through this endpoint.

## Reconciliation flags for the `listings`/`orders` batch coordinators

- **`status` filter semantics differ by design, not bug, between `GET /sellers/me/listings` (raw `ListingStatus`) and whatever the `listings` module's `getMyListings(tab, …)` groups as a tab** — see endpoint 21's note and `BRI-307`. Confirm the `listings` batch's own doc agrees these are deliberately two different groupings.
- **Ownership-violation error code is inconsistent WITHIN this module**: `GET /sellers/me/orders/:id` returns a flat `404` for a non-owned order id; `PATCH /sellers/me/orders/:id/status` (delegated to `OrdersService.updateStatus`) returns `403` for the identical ownership mismatch. Same for `approve-cancellation`/`deny-cancellation` (also `403` via `OrdersService`). Worth a cross-module security-review note, not just a QA scenario.
- **`UpdateOrderStatusDto.trackingUrl`** is `@IsUrl`-validated (orders module DTO) while `ShipOrderDto.trackingUrl` (sellers module DTO, used by the dedicated `ship` endpoint) is a plain unvalidated string — two different validation strictness levels for the same conceptual field, reachable via two different sellers-controller routes that both ultimately set `Order.trackingUrl`.
