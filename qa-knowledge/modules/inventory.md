# Module: inventory (`apps/api/src/inventory/`)

4 endpoints, all under `@Controller('seller/inventory')` with a **class-level** `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('SELLER')` (`inventory.controller.ts:14-15`) — every route in this module requires an authenticated, confirmed seller; there is no public or admin-facing route here at all. Paired module: `listings` (see `modules/listings.md`) — `InventoryService` depends on `ListingsService` (constructor injection, `inventory.service.ts:9-10`) to sync the Qdrant embedding index whenever a status flip happens as a side effect of an inventory write; `ListingsRepository` is used directly by `InventoryRepository` for the shared `NOT_DELETED` filter, which is a same-module-family exception to the "don't reach into another module's repository" rule — acceptable here because `inventory` and `listings` are tightly coupled by the `Listing ⟷ Inventory` 1:1 relation and `InventoryRepository` only ever reads `NOT_DELETED` as a shared constant, not another module's repository methods.

Source files read in full: `inventory.controller.ts`, `inventory.service.ts`, `inventory.repository.ts`, `inventory.service.spec.ts`, `inventory.repository.spec.ts`, `dto/update-inventory.dto.ts`, `dto/get-inventory-query.dto.ts`. Also read: `apps/api/prisma/schema.prisma` (`Inventory`, `InventoryAdjustmentHistory` models), `apps/api/prisma/manual-sql/2026-08-31-repair-leaked-inventory-holds.sql`, `apps/web/src/lib/sellerApi.ts`, `docs/api-todo.md`, `docs/repository-health-review.md`.

## The inventory model

`Inventory` (`schema.prisma:1316-1325`, 1:1 with `Listing`, `onDelete: Cascade`): `onHand` (default 1), `committed`, `unavailable` — **`available` is never stored**, always derived as `available = max(0, onHand − committed − unavailable)` (`apps/api/CLAUDE.md`'s documented invariant, confirmed in both `InventoryService` and `InventoryRepository`). A `Listing` with no `Inventory` row yet (pre-dates the feature, or has never been touched by a hold) falls back to `Listing.stock` as its effective `onHand` (`inventory.service.ts:17,55`, `inventory.repository.ts:134-135,229-230`) — **every mutation method seeds a real `Inventory` row from `stock` via `upsert` on first touch**, so this fallback is transient, not a permanent parallel source of truth.

`InventoryAdjustmentHistory` (`schema.prisma:1751-1767`): append-only audit log, one row per manual quantity change (`adjustmentType: 'manual'`, `notes: 'Updated via seller portal'`, `createdById` = the seller). `locationId` exists on the model (multi-location inventory) but is never populated by any of these 4 endpoints — always `null` from this module (confirmed: `inventory.repository.ts:75-84` never sets it). Out of scope for this module: `ListingLocationInventory`/`Location` (a separate, apparently unused-by-this-module multi-location feature visible only in the schema).

### The four mutation primitives NOT exposed by this controller

`InventoryRepository` defines `incrementCommitted`, `decrementCommitted`, `commitForReservation`, and `decrementOnHand` (`inventory.repository.ts:132-278`) — these are the real hold/release machinery, called from the **offers** and **orders** modules (out of this batch's scope; cross-referenced here because they are the direct subject of the historical production incident documented in `prisma/manual-sql/2026-08-31-repair-leaked-inventory-holds.sql`, see Business Rules). None of the 4 REST endpoints in `inventory.controller.ts` call them directly — `GET`/`PUT /seller/inventory/listings/:id` only ever call `upsertAvailable` (a manual-edit path), never the hold primitives. A tester validating hold/release behavior (Buy Now reservation, offer-accept, order cancellation, order delivery) must do so through the **offers**/**orders** endpoints, not through this module's own routes — this module only observes and manually overrides the result.

## Endpoint-by-endpoint

### `GET /seller/inventory` — `inventory.controller.ts:20` → `InventoryService.getInventory` (`inventory.service.ts:13`)
- **Guard**: class-level `JwtAuthGuard, RolesGuard` + `@Roles('SELLER')`.
- **DTO**: `GetInventoryQueryDto` — `page`≥1 (default 1), `limit` 1–**100** (default 20) — note this ceiling is **double** `GET /listings`'/`GET /listings/mine`'s 50-cap; not wrong, just an inconsistency worth knowing when writing pagination boundary tests across modules.
- **Repository**: `findBySellerId` — all non-deleted listings for the seller (`NOT_DELETED` from the `listings` module's own constant, not re-derived here), `include: { images: take 1, inventory: true }`, ordered `createdAt desc`, real `skip`/`take` + a separate `count`, both issued but **not wrapped in one `$transaction`** (unlike every paginated query in the `listings` module, which does use `$transaction([findMany, count])`) — a small window exists where `total` and the page of `data` could reflect two slightly different moments under heavy concurrent writes; low practical risk (seller-scoped list, not a hot public feed) but a genuine inconsistency with the sibling module's pattern.
- **Self-healing read**: for every row in the page where `available > 0` AND `listing.status === 'sold'` (a drift state — inventory says sellable but the listing row still says sold), the service batches those ids into `syncSoldToActive` and flips them back to `active` **as a side effect of a GET request**, then syncs the embedding index for each one actually flipped. This is a deliberate repair-on-read pattern (confirmed by `inventory.service.spec.ts:35-50`), not an accidental write — but it does mean **a plain list read can mutate listing status**, which matters for any test that asserts "GET is read-only" as a general property; it is not, for this one endpoint, by design.
- **Response shape**: `{data: [{listingId, title, imageUrl, status, onHand, committed, unavailable, available}], total, page, limit}`.
- **Frontend**: web `sellerApi.getInventory` (`apps/web/src/lib/sellerApi.ts:459-461`) is **defined but has no caller** in the analyzed `apps/web/src` tree (`grep` for `getInventory` outside `sellerApi.ts` returns nothing) — `apps/web/CLAUDE.md` confirms the standalone "seller Inventory" page was **removed** (not moved) from the web app's routing standards, so this client method is now dead code left over from that removal. **No mobile caller at all** — `apps/mobile/src/services/` has no inventory API file (confirmed: no `grep` hit for `seller/inventory` anywhere under `apps/mobile/src`). **"No frontend reference found in the analyzed scope"** is the accurate characterization for this endpoint today — it is reachable only by a direct API call, not through either shipped client.

### `GET /seller/inventory/listings/:listingId` — `inventory.controller.ts:26` → `InventoryService.getListingInventory` (`inventory.service.ts:50`)
- **Guard**: class-level, same as above.
- **Ownership**: `findListingByIdAndSeller(listingId, sellerId)` — plain `findFirst({id, sellerId})`, **no `NOT_DELETED`/soft-delete filter applied here** (unlike the `listings` module's own `findByIdForOwner`, which always spreads `NOT_DELETED`). This means a **soft-deleted** listing the seller once owned can still have its inventory read via this endpoint (and, see below, written via the `PUT` sibling) even though it's invisible everywhere else (BRI-366). Worth a dedicated negative test — see Gaps.
- Same self-healing sold→active repair as the list endpoint, scoped to the one listing.
- **Response**: `{listingId, onHand, committed, unavailable, available}`.
- **Frontend**: web `sellerApi.getListingInventory` — consumed inline by the seller's **listing edit page** (`apps/web/src/app/seller/listings/[id]/edit/page.tsx:85`), not a dedicated inventory page (that page was removed; stock is now edited as one field on the regular listing edit form). No mobile caller found.

### `PUT /seller/inventory/listings/:listingId` — `inventory.controller.ts:35` → `InventoryService.updateListingInventory` (`inventory.service.ts:70`)
- **Guard**: class-level, same as above. **DTO**: `UpdateInventoryDto` — `quantityAvailable: number`, `@IsInt() @Min(0)`, with a `@Transform` that runs **before** validation and clamps any non-numeric/negative/garbage input to `0` (`Math.round(Math.max(0, Number(value) || 0))`) — so a client sending `"abc"` or `-5` never reaches the `@IsInt`/`@Min` check as a validation failure; it silently becomes `0` and succeeds. This is a deliberate defensive-clamp pattern, not a validation bug, but it means **the 400 "quantityAvailable must be an integer" path is effectively unreachable from this DTO** — any would-be-invalid input is coerced to a valid one before class-validator ever sees it. A test expecting a 400 on bad input here will not get one; it will get a 200 with `onHand` recomputed as if `0` was sent.
- Same ownership check as the `GET` sibling (`findListingByIdAndSeller`, **no soft-delete filter**).
- **Write semantics (PRD formula, confirmed in code comment at `inventory.repository.ts:46`)**: `newOnHand = quantityAvailable + committed + unavailable` — i.e. the seller is editing *available* stock, and the repository back-solves `onHand` to make that true while **leaving `committed`/`unavailable` exactly as they were**. A seller cannot free a held unit or clear an "unavailable" flag through this endpoint; those are mutated only by the (out-of-module) hold/release primitives.
- **Entire write is one `$transaction`** (`inventory.repository.ts:38-87`): read existing (for `oldAvailable`, used only for the history row), upsert `Inventory.onHand`, conditionally flip `Listing.status` (`active`/`approved` → `sold` iff the new `available` is `≤0`; `sold` → `active` iff the new `available` is `>0` — **`reserved` is never auto-flipped by this path**, only `active`/`approved`↔`sold`), then write one `InventoryAdjustmentHistory` row — all four writes commit or roll back together, so a crash mid-update cannot leave `Inventory` and `Listing.status` disagreeing.
- The repository reports back whether a status flip **actually happened** (`result.count > 0`, not merely "we asked for one") — the service only syncs the embedding index when a real flip occurred, never speculatively.
- **Response**: `{listingId, onHand, committed, unavailable, available}` (same shape as `GET`).
- **Frontend**: web `sellerApi.updateListingInventory` — consumed inline by the seller's listing edit page (`apps/web/src/app/seller/listings/[id]/edit/page.tsx:199`, a plain "Stock" field on the edit form, `.catch(() => {})` — a failed inventory update is silently swallowed and does not block the rest of the listing-edit save; worth a test). No mobile caller found.

### `GET /seller/inventory/listings/:listingId/history` — `inventory.controller.ts:46` → `InventoryService.getListingHistory` (`inventory.service.ts:90`)
- **Guard**: class-level, same as above. Ownership check identical to the other two listing-scoped routes (same no-soft-delete-filter caveat applies).
- Returns every `InventoryAdjustmentHistory` row for the listing, newest first, with `createdBy: {id, name}` joined in. No pagination at all on this endpoint (unbounded `findMany`) — for a listing with a very long manual-adjustment history this has no page size cap; low practical risk today (manual edits are infrequent per listing) but a latent unbounded-query gap if adjustment frequency ever increases (e.g., if a future feature writes a history row per hold/release too, not just manual edits).
- **Frontend**: web `sellerApi.getListingInventoryHistory` (`sellerApi.ts:474-476`) is **defined but has no caller** found anywhere in `apps/web/src` outside `sellerApi.ts` itself — same "removed inventory page" situation as the list endpoint. No mobile caller. **"No frontend reference found in the analyzed scope."**

## Historical incident (directly in scope for this module)

`prisma/manual-sql/2026-08-31-repair-leaked-inventory-holds.sql` documents a confirmed past production data-integrity bug: three **admin** endpoints (`PATCH /admin/orders/:id`, `POST /admin/orders/:id/resolve-dispute`, `POST /admin/orders/:id/issue-refund` — all in the `admin`/`orders` modules, out of this batch's scope) used to write `Order.status` directly on the admin repository, bypassing `OrdersService` entirely — so an order moved to `delivered`/`cancelled` by an admin never called `decrementOnHand`/`decrementCommitted`. `Inventory.committed` stayed held forever against a concluded sale, which zeroed `available` on a listing whose own row still read `active`/`stock ≥ 1` — `OffersService.assertStillAvailable` (offers module) then refused every subsequent accept/counter on that listing with a false "This item has already sold" 409, while every buyer-facing screen still showed it as live. A **second**, related leak is also fixed in the same commit family: `decrementCommitted`/`decrementOnHand` used to use Prisma's unbounded `{decrement: qty}`, so any code path that released the same hold twice drove `committed` negative (observed `-1` to `-3` on real rows in a shared dev database) — a negative `committed` inflates `available` and is the oversell side of the identical coin. Both are now defended in the current code read for this analysis: `GREATEST(..., 0)` floors directly inside the raw `UPDATE` statements in `decrementCommitted`/`decrementOnHand` (`inventory.repository.ts:182-186,270-276`), chosen specifically over a read-then-floor-in-JS approach because the latter gives up atomicity under concurrent releases (a documented, reasoned engineering choice, not an oversight). The repair SQL itself is additive/idempotent (caps `committed` down via `LEAST`, never raises it; re-running it twice is a no-op) and deliberately does **not** touch `onHand` or flip any listing's status back to sellable automatically — both are called out in the file as requiring a human decision per listing, routed through this very module's `PUT /seller/inventory/listings/:listingId` (`upsertAvailable`, which recomputes both counters and the listing status together, with an audit row).

**This module's own 4 endpoints were never implicated in the incident** — the leak was entirely in the bypassed admin/order write path, and this module's `upsertAvailable` already recomputed `onHand`/status/history atomically in one transaction before, during, and after the incident. Flagged here because (a) the fix this module's code already carries (the `GREATEST` floors) is the permanent guard against the leak recurring through *any* caller of `decrementCommitted`/`decrementOnHand`, including future ones, and (b) a tester validating "inventory correctness" for this feature area should know the historical failure mode lived one module over, in code this batch did not re-analyze line-by-line (orders/admin — a different batch's scope per `qa-knowledge/progress.md`).
