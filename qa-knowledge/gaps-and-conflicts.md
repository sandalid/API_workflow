# Gaps and Conflicts

Consolidated from all 31 module docs during the 2026-11-10 continuation session. Every item below cites its source `modules/<name>.md` and, where applicable, the underlying `business-rules.json` rule id and Linear ticket. Items are grouped by kind, not by module, so a reviewer can scan for "what's actually broken/missing" vs. "what's just inconsistent" vs. "what's a tracker artifact" without re-deriving the categorization per module.

**Read this file as a punch list, not a bug report.** Several items here are deliberate, signed-off product decisions (documented as such) rather than defects — each entry says which.

## 4. Inconsistent enforcement of the *same* business rule across modules

Not bugs in either individual location, but worth a cross-module test specifically because the two call sites can drift independently.

- **Self-dealing (seller can't transact on their own listing) uses two different HTTP statuses for the identical rule**: `OffersService.createOffer`/`createWalletHoldIntent` → **400 Bad Request**; `OrdersService.create` → **403 Forbidden**. Same business rule (`BRI-54` Business Rule 12), two different status codes depending on which module you hit. (`BR-OFFERS-008`, `BR-ORDERS-002`)
- **Ownership-mismatch status codes disagree within the `sellers` module itself**: `GET /sellers/me/orders/:id` → 404 for a non-owned order; `PATCH /sellers/me/orders/:id/status`/`.../approve-cancellation`/`.../deny-cancellation` → 403 for the identical kind of violation. 403 confirms the resource exists where someone else owns it; 404 doesn't — a real, if minor, information-disclosure inconsistency. (`BR-SELLERS-016`)
- **`trackingUrl` validation strictness differs by which route sets it**: `@IsUrl()` via the `orders` module's `UpdateOrderStatusDto`, plain unvalidated string via the `sellers` module's `ShipOrderDto` — both ultimately write the same `Order.trackingUrl` column. (`BR-SELLERS-019`)
- **Referential-integrity delete guards are inconsistent across sibling taxonomy resources in `admin`**: `deleteCategory`/`deleteBrand` block on live listing references (409 + count); `deleteSubcategory`/`deleteType` do not (cascading delete, no check); `deleteMaterial` correctly has no check (free-text field, nothing to orphan). The subcategory/type gap is unresolved — may be intentional if listings only ever reference the leaf type, not re-verified either way in this pass. (`BR-ADMIN-003`)
- **`isDefault`-style dead fields appear in two unrelated modules**: `PaymentMethod.isDefault` (no setter anywhere — `BR-PAYMENT-METHODS-007`) and `PaymentMethod` sort-key reliance generally. Not the same field, but the same shape of latent dead functionality — worth a single sweep if a future pass wants to find more.
- **"GET as side-effecting read" appears independently in three modules**, each its own lazy-sweep pattern with no shared mechanism: `connect.getStatus` (retries failed payouts + live Stripe reconciliation on every read), `sellers.getOrderById` (can auto-approve a stale cancellation request), `inventory`'s list/detail reads (self-heals a sold/active drift state). None of these are bugs individually (each is documented as deliberate), but a test suite assuming "GET is read-only" as a blanket invariant will be wrong for all three — and a *fourth*, `orders.findById`/`findAllByBuyer`/`findAllBySeller`, runs **every** lazy sweep (cancel auto-approve, ship-timeout, receipt auto-confirm, carrier poll, transfer retry) on every single read.
- **Lazy-on-read-only sweeps with no cron** recur across `orders` (24h cancellation auto-approve, 3-day receipt auto-confirm, 7-day seller-never-shipped auto-cancel) and `disputes` (24h evidence-window advance, 5-day return-ship auto-release). Every one of these has the identical shape of risk: if nobody opens the relevant record, the time-based transition never fires. `BRI-516` and `BRI-591` are the two open Linear tickets documenting this exact gap for the `orders` side; no equivalent ticket was found for the `disputes` side despite the mechanism being structurally identical — worth filing or at least flagging during triage.

## 5. Dead/unreachable code (fully implemented, not called by any shipped frontend)

Distinct from "gap" — these are endpoints or code paths that work correctly but have no live caller today. Useful for test-prioritization (low product risk if broken) and for knowing not to be surprised when a grep finds no screen.

- `POST /auth/signup` and `POST /auth/login` (direct email/password) — no production mobile caller found; the real buyer flow is entirely OTP-based (`POST /auth/otp/verify`). `POST /auth/login` is invoked in production **only** by the Next.js admin-login server route, never a browser-facing client wrapper.
- `POST /ai/regenerate` — fully implemented and unit-tested on both API and mobile sides, but no mobile screen calls it (confirmed by grep); the backend's own comment says exactly this.
- `POST /sellers/me/seller-reviews/:id/reply` — fully built end-to-end, zero UI anywhere (see § 2 #16 above).
- `DELETE /users/me/deletion` (cancel a pending deletion) — reachable, correctly implemented, but the `DeleteAccountScreen` has no "cancel" button; the only live cancel path is the automatic one inside sign-in.
- `GET /users/:id/listings` — see § 1 #20.
- `GET /seller/inventory` and `GET /seller/inventory/listings/:listingId/history` (web) — defined client methods with no caller anywhere in `apps/web/src` outside `sellerApi.ts` itself; the standalone seller Inventory page was removed from web's routing.
- `GET /auth/dev/otp`, `GET /users/me/deletion/dev-code`, `POST /seed/run`, `POST /embeddings/backfill`/`reconcile` — all QA/ops-automation-only by design, no app-code caller expected (confirmed absent, consistent with intent).

## 6. Safety-relevant findings worth repeating here even though they're not "gaps"

- **`POST /seed/run` is additive/idempotent by construction** — zero destructive Prisma calls found across its 765-line implementation (verified by direct read, not inferred). Safe to call repeatedly against an environment with pre-existing data, **conditioned on** `NODE_ENV !== 'production'` being the *only* access control (see next item).
- **Three dev-only operational endpoints share one access-control pattern with no identity check**: `POST /seed/run`, `POST /embeddings/backfill`, `POST /embeddings/reconcile` are gated solely by `NODE_ENV !== 'production'` — in any non-production environment, anyone who can reach the host can call them. `GET /auth/dev/otp` and `GET /users/me/deletion/dev-code` layer the same environment gate on top of `JwtAuthGuard` (a stricter variant, scoped to the caller's own data).

## 7. Documentation/process corrections made during this consolidation pass

- **This knowledge base's own original docs survey was too shallow.** `overview.md`'s first pass used `find docs -maxdepth 1`, missing `docs/fix/` (100+ per-ticket write-ups) and `docs/features/` (80+ feature specs) entirely. These are real and are the actual source several module docs (starting with `offers.md`) drew their BRI-citation depth from — confirmed, not fabricated, on inspection. Corrected in `overview.md`; any of the 15 earliest-written module docs that predate this correction should be spot-checked against `docs/fix/<module>/` and `docs/features/` before being treated as exhaustively cross-referenced.
- **The idempotency claim in `overview.md` was wrong and has been corrected.** The original text ("the API has no idempotency keys yet") uncritically copied `apps/mobile/CLAUDE.md`'s own framing without checking source. Stripe-operation idempotency is extensively implemented and tested (checkout, offer holds, every Connect transfer/reversal/refund); only *generic API-request-level* idempotency (an `Idempotency-Key` header/platform middleware) is genuinely absent. See `BR-IDEMPOTENCY-GLOBAL-001` in `business-rules.json`.
- **The `offers.md` inventory-commit contradiction flagged by the user was resolved**, not by picking one of two conflicting statements, but by reading `offers.service.ts:904-1127` directly: acceptance does commit inventory (step 12/15 of `acceptOffer`, after capture+order-creation+status-flip succeed); the "acceptance commits no inventory" source comment describes only the instant *before* that step, within a concurrent-accept race. See `BR-OFFERS-012b` and the Correction callout in `modules/offers.md`.
- **The admin URL surface is fragmented across five controllers** (`admin.controller.ts`, `disputes.controller.ts`'s `dispute-cases*`, `messaging.admin.controller.ts`, `reviews.controller.ts`'s admin routes, `feed/curation.controller.ts`) — all mounted under the `admin/*` prefix but owned by different domain modules. Not a defect, but worth stating plainly: `modules/admin.md`'s 56 endpoints are **not** the complete admin surface.
- **Three peer Claude Code sessions in this workspace** (`schemathesis-b4`, `api-workflow-7b`, `api-automation-8e`, plus a forked "Post-audit schema testing and API automation" session) were observed running in this workspace at the start of this analysis, apparently on related API-testing/automation work. This knowledge base was built independently and was **not** coordinated with them — if their output overlaps or conflicts with this one, reconcile before treating either as authoritative.

## 8. Known execution blockers for a future testing agent

- The `shippo` MCP server failed to connect during this analysis (`CONNECT_TIMEOUT`) — any test setup that would benefit from inspecting Shippo's own sandbox/test-webhook tooling directly cannot do so from this environment; confirmed as an environment issue, not evidence that Shippo integration itself is unavailable in the product.
- `prisma/manual-sql/2026-10-27-fix-review-unique-order-constraint.sql`'s own write-up explicitly states the real QA database's constraint-patch status was **not confirmed** as of that fix — a test run against a QA-like environment hitting an unexpected 500 on every review submission should check this specific constraint before assuming a new regression (see `BR-REVIEWS-015`).
- Package dimensions are not collected anywhere in the current listing-creation flow (confirmed across `disputes.md` and `sellers.md` independently) — any test scenario that depends on a *real* (non-mock) Shippo return or outbound label requires either seeding dimensions directly in the DB or treating the mock-label path as the only testable one today.
